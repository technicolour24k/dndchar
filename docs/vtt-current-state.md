## 1. Session Model - ✅ As designed, 🔁 extended

In-memory only (`globalThis.__vttStore__`), exactly per spec - a server restart wipes every room, and that's accepted as fine for a POC.

**Why `globalThis` instead of a plain module-level object:** `vtt/server/store.js` has to be importable unmodified from three different loading contexts in the same process (SvelteKit's `$vtt`-aliased routes, the Vite dev plugin, and prod `server.js`). If the module gets loaded more than once under different specifiers, a plain top-level `const sessions = new Map()` could end up as two separate Maps. Stashing state on `globalThis` guarantees all three paths share it. This wasn't in the spec because the spec assumed a single standalone process - see Section 6 for the bigger structural reason.

Shape actually in use (`createSession`, `vtt/server/store.js`):

```js
{ id, gmSocketId: null, map: null, tokens: {}, players: {}, markers: {} }
```

Deviations from the spec's example JSON:
- **`markers: {}`** - new top-level collection, not in spec. See Section 8 (features beyond spec).
- **Token fields added**: `visionTrueFt`, `visionDevilFt` (truesight / devil's sight - see truncated all-or-nothing radius override in Section 4), `speedFt` / `speedRemainingFt` (movement budget), `condition` (`healthy`/`bloodied`/`critical` - spec Section 5 *suggested* this, it's now actually built). `imageUrl` is mutable post-creation via `token:stat:update`, not just at `token:add` time.
- Room codes exclude visually ambiguous characters (`0/O/1/I`) - refinement, not a deviation.
- `players[id]` doesn't store `socketId` directly (spec's example does) - connection identity lives on the per-socket `meta` object instead. Functionally equivalent, structured differently.

**How to verify**: open two browser tabs, create/join a room, and inspect the WS frames in devtools - `state:full`'s `session` payload shows the shape above.

## 2. Room Creation & Join Flow - ✅ As designed, 🔁 one gap

`POST /vtt/api/session` (`src/routes/vtt/api/session/+server.ts`) matches spec verbatim: plain HTTP, generates a code, creates the session, returns `{ sessionId }`.

Join (`vtt/server/handlers/join.js`):
- `join:error` / `reason: 'session_not_found'` on bad code - matches spec's example payload exactly.
- `state:full` sent to the joining socket only, filtered through `filterSessionForRole`, on **the same code path** for fresh join and reconnect - this was the spec's explicit ask ("eliminates most special-case resync bugs") and it's honored.
- `player:joined` broadcasts to everyone *else* in the session, player-role joins only (a GM join doesn't emit it).
- GM claim: (Quick rooms; campaign rooms use the ticketed seat described below) first GM claim wins, matching spec's "whoever connects first as GM claims the role, no auth needed." **Now enforced** (Phase 2 Section 0b, see below) - a second live GM socket is rejected with `join:error`/`gm_already_claimed`; a stale claim (GM disconnected, nothing currently holds it) is reclaimable.
- **Disconnect cleanup** (Phase 2 Section 0c): a departing player broadcasts `player:left` and is marked `connected: false` (not deleted - they reappear correctly on reconnect); a departing GM clears `gmSocketId` so 0b's reclaim logic can pick up a new one.

**🔁 Real deviation from spec's assumed standalone flow**: joining now goes through the app's account system. `/vtt` (`src/routes/vtt/+page.server.ts`, since Campaigns F a lobby page, not a redirect) is an authenticated SvelteKit route; its Quick room link opens the static client with `?playerId=&playerName=` pre-filled from the logged-in user, so nobody types a name manually when arriving via the nav link. Opening `/vtt-app/index.html` directly still works with manual entry + a random per-browser id, which is how the spec originally envisioned it and remains useful for quick multi-tab testing.

**Campaign tables (campaign-system Units E and F, 2026-11-20)**: a campaign has one long-lived room with a fixed 8-character code, joined only with a one-use ticket. `/vtt` is now a lobby (`src/routes/vtt/+page.svelte`): the user's real campaign memberships (same search and 12-per-page pager as `/campaigns`, membership only even for an admin) with "Open as DM" (dm / co-DM) and "Open as player" links to `/vtt-app/index.html?campaignId=&role=gm|player&playerId=&playerName=`, plus a "Quick room" link that is the old flow unchanged. A page opened with `?campaignId=` hides Create/Join; `static/vtt-app/campaign.js` POSTs `/vtt/api/campaigns/<id>/ticket { role, takeoverOf: 'self' | 'co' }` (membership checked there: the site admin override does not apply) and joins with `{ type: 'join', sessionId, ticket }`. User id, display name, role and GM-seat rank come from the ticket; what the client sends is ignored, and a ticket-less join to a campaign room gets `ticket_required`. Tickets are single use and last 60 seconds, so every connect and reconnect fetches a fresh one (`bad_ticket` fetches one more and retries once). GM seat (one per room): the primary DM takes it, the co-DM when the primary is absent; `gm_seat_taken` (`canTakeOver`, `heldBy: 'self' | 'other'`) means a takeover is possible. The client takes over quietly when the holder is the user's own older socket and the connect is automatic (a reconnect, or a reload of a tab that had the table, remembered in sessionStorage), asks "You already have this table open elsewhere" for a fresh open, and always asks when the co-DM holds it ("Your co-DM is running the table"). The ticket's `takeoverOf` is applied only if it matches who holds the seat at join time. A takeover is never repeated by a later reconnect, and a replaced tab forgets its reload marker and turns its URL into a player link, so a refresh doesn't win the seat back. The replaced socket gets `gm:replaced` and close code 4002 and rejoins as a player with a banner. `kicked` (close 4001) with `removed_from_campaign` stops with "You're no longer in this campaign..." and no reconnect; `role_changed` reconnects with a fresh ticket (a 403 `not_dm` falls back to player). Quick rooms still use the old path.

**How to verify**: log in, click **VTT** in the nav, note the room code in the sidebar. Open a second browser (or a different logged-in account) and join with that code - confirm `player:joined` fires (visible in the first tab's sidebar player list and in devtools WS frames). Try a bogus code in a third tab and confirm `join:error`. Kill and reopen a tab's connection with the same code to confirm reconnect replays `state:full` correctly.

## 3. Core Event Types - 🔁 5.5 of 6, plus one net-new family

All handlers live in `vtt/server/handlers/{token,map,marker}.js`, dispatched from a switch in `wsServer.js`, following the spec's validate→mutate→broadcast(filtered) pattern with no per-feature bespoke plumbing.

| Event | State | Notes |
|---|---|---|
| `map:set` | ✅ | GM-only gate (`meta.role !== 'gm'` → reject). Broadcasts unfiltered - matches spec (map has no secret fields). |
| `token:add` | 🔁 | GM (any) **or a player adding a `pc` token for themselves** (Phase 2 Section 1a — see below). Filtered per-recipient. |
| `token:remove` | ✅ | GM-only. A hidden token's removal is invisible to players who never knew it existed. |
| `token:move` | ✅ | GM (any token) or player (`canEditToken`: `token.ownerId === meta.playerId`) - matches spec's payload shape exactly. Optional `waypoints` for path moves (2026-11-19). Related: `token:recenter` (free, server-computed map centre) and the ephemeral `token:move:preview` / `token:move:preview:clear` relays. |
| `token:stat:update` | 🔁 | GM (any) or owning player, now field-limited via an allowlist (Phase 2 Section 0a) - see updated caveat below. |
| `token:hidden:toggle` | 🔁 | GM-only. Improves on the spec's literal wording - see snippet below. |
| `fog:reveal` / `fog:hide` | ⛔ | Not implemented - no handler, no client code. Spec explicitly marked this optional ("if doing manual fog on top of vision") and no milestone exercises it, so this is a deliberate skip, not an oversight. |
| `target:select` / `target:clear` | ✅ | Phase 2 Section 3a. Any joined socket may send it - no ownership/role check, per the spec's own "weakest validation in the codebase" framing. Thin pass-through, rebroadcast verbatim. |

**`token:stat:update` caveat (resolved in Phase 2)**: previously, `canEditToken` verified ownership only, not which `stat` key was being written. Phase 2 Section 0a added `PLAYER_EDITABLE_FIELDS`/`isFieldEditAllowed(role, isOwner, field)` in `vtt/server/handlers/token.js` - a player can now only write `hp`, `maxHp`, `speedRemainingFt`, `visionNormalFt`, `visionDarkFt`, `x`, `y`, `spellSlots` on their own token; everything else (`condition`, `defeated`, `ac`, `saves`, `actions`, `characterId`, `preparedSpells`, any other free-form `stats.*` key) is GM-only by default. Disallowed writes get an explicit `token:stat:update:error` back to the sender instead of silently no-oping. Note `hp`/`maxHp` are deliberately included in the player-editable list - that's pre-existing, already-shipped self-service HP tracking, not the risk this allowlist closes (see Phase 2 section below for the reasoning).

**`token:hidden:toggle` improvement over spec**: rather than literally broadcasting a toggle event to players (which would leak "something changed here" even if the token's other data is hidden), the server translates it into the same `token:add`/`token:remove` events players already handle:

```js
// vtt/server/handlers/token.js
return token.hidden
  ? { type: 'token:remove', tokenId: token.id }
  : { type: 'token:add', token: filterTokenForPlayer(token) };
```

**How to verify**: as GM, add a `type: enemy` token with **Hidden from players** checked - watch the player tab's WS frames (not just the UI) and confirm no message ever references it. Uncheck it and confirm a `token:add` appears in the player's frames.

## 4. Vision & Blackout Rendering - ✅ As designed, 🔁 extended, 🔁 **rearchitected 2026-07-30**

Still computed client-side per-player (unioned across owned tokens), never on the server - matches spec's core architectural call. But the *rendering* of the mask moved off the canvas entirely (per `.claude/briefs/vtt-map-rendering-rearchitecture-spec.md`, to support video/animated map backgrounds): the map is now layered DOM elements (`<img>`/`<video>`) behind a transparent canvas, composited by the browser - black backdrop, grayscale-filtered map layer clipped to the union of gray-band circles (SVG `<clipPath>`, one `<circle>` per owned token), full-color map layer clipped to the color-band union on top. See `static/vtt-app/render/mapLayers.js` and the 2026-07-30 changelog entry.

`computeVisionRadii(ownedTokens, map)` (unchanged, still in `vision.js`) derives `colorRadius`/`grayRadius` per token; those radii now feed SVG clip-circle geometry instead of canvas draw passes. Multi-circle union correctness comes from the SVG spec (multiple shapes in one `<clipPath>` union automatically) rather than draw-pass ordering (spec milestone 9 still holds).

`map.brightness` handling matches the three spec-defined modes, **corrected post-launch** (see changelog) to follow 5e RAW's darkvision text more faithfully - darkvision sees dim light as if it were bright light (full color), and true darkness as if it were dim light but explicitly without color (grayscale only):

```js
if (brightness === 'dim') {
  colorRadius = darkFt * pxPerFoot;               // darkvision = full color in dim light (RAW)
  grayRadius = Math.max(normalFt, darkFt) * pxPerFoot;
} else if (brightness === 'bright') {
  colorRadius = Math.max(normalFt, BRIGHT_LIGHT_RADIUS_FT) * pxPerFoot;   // 150ft floor, no gray band
} else { // 'dark'
  colorRadius = normalFt * pxPerFoot;
  grayRadius = darkFt > normalFt ? darkFt * pxPerFoot : colorRadius;
}
```

The original POC version had `colorRadius = 0` unconditionally in `dim` mode (everyone grayscale, no exception for darkvision) - the spec itself flagged this as an allowed simplification ("POC can skip nuance here... if easier"), but it produced a genuinely backwards result: a darkvision creature got *less* color in dim light than in true darkness, when RAW says the opposite (dim = as bright for darkvision; darkness = grayscale only, never color). Fixed so `dim` mode's color radius depends on `darkFt`, same as everything else already did.

**🔁 Extension beyond spec**: `bright` mode's color radius is no longer capped at the token's own `visionNormalFt` (typically 30ft) - it now uses a 150ft floor (`Math.max(normalFt, 150)`), following a user observation that 5e doesn't actually cap unaided daylight sight at a fixed distance the way it caps darkvision; `visionNormalFt` is a POC fog-of-war convenience, not a RAW-defined range, and 30ft made outdoor daylight scenes feel far more constrained than they should. `dim`/`dark` are unaffected - vision genuinely is the meaningful constraint there, which is exactly where the token-specific radius stat should still apply.

Hard-edged circles, no soft falloff - exactly what the spec allowed for POC simplicity.

**🔁 Extension beyond spec**: `visionTrueFt` (truesight) and `visionDevilFt` (devil's sight) were added as extra vision bands not in the original spec. Both extend the color/gray radius regardless of brightness (`colorRadius = Math.max(colorRadius, specialRadius)`), modeling "sees clearly even in darkness/magical darkness."

GM view is unmasked (full map, all tokens including hidden) - `main.js`'s render loop branches on `role === 'gm'` and skips vision masking entirely.

**🔁 Extension**: zoom (25%-400%, buttons + ctrl/cmd+scroll) and pan (scroll) were added. The spec doesn't mention zoom/pan at all - it implicitly assumed a 1:1 canvas. This is a **pure CSS scale** of the canvas element; the backing pixel buffer stays at the map's native size (`static/vtt-app/main.js:44` comment: *"CSS-only scale of the canvas; the backing pixel buffer stays at native map size"*), so vision-mask math and click/drag coordinate translation (`canvasCoords()`) both operate in unscaled map-space and divide out the zoom factor - vision rendering itself is zoom-agnostic. Note: `vtt/README.md` currently still says "No zoom/pan" under "Known POC gaps" - that line is **stale** and should be corrected next time the README is touched.

**How to verify**: give a player two tokens placed far apart with different `visionNormalFt`/`visionDarkFt`, confirm the revealed area is the union of both circles, not just the most-recently-moved token's. Toggle `map.brightness` via a `map:set` and confirm the three modes render as described.

## 5. Filtering - ✅ As designed, fully implemented, no gaps found

`filterSessionForRole(session, role, playerId)` lives exactly where spec asked (`vtt/server/store.js`), and is applied both on `join`'s `state:full` and on **every** token/marker-bearing broadcast (via `filterTokenForPlayer`/`broadcastToken` in `token.js`, and an analogous `shouldPlayerSeeMarker` for the new marker feature) - not client-UI-only.

```js
export function filterTokenForPlayer(token) {
  if (token.type === 'enemy' || token.type === 'npc') {
    const { stats, ...rest } = token;
    if (token.condition !== undefined) rest.condition = token.condition;
    return rest;
  }
  return token;
}
```

`stats` is genuinely absent from the payload (key omitted, not zeroed/nulled) for enemy/npc tokens sent to players; hidden tokens are dropped outright. This is the one spec mandate ("the one function to get right") that's fully and consistently honored everywhere it needs to be, including in the marker feature that didn't exist when the spec was written.

**How to verify**: same steps as Section 3's hidden-token check, plus: set HP on an enemy token as GM, confirm the player's WS frames never carry a `stats` key for that token, only `condition` if one's been set.

**As designed, matching spec's original intent**: PC tokens' `stats` are sent over the wire unfiltered to all players (matches the spec's "HP isn't secret between allies" stance), and the client displays that real HP bar/number for any `pc` token regardless of owner - enemy/npc tokens fall back to the coarse `condition` badge since `stats` was never sent for them in the first place. A 2026-07-14 change briefly made the client hide non-owned PC HP too (uniform "no raw HP unless you own it" rule); that was reverted 2026-07-29 as a deliberate policy call, back to this original type-based split - see the "Raw HP no longer shown..." and "Revert: PC HP visible to all players again" changelog entries below.

**Why `vtt/server/*.js` is untyped JS living outside `src/`**: it has to be imported unmodified from three different contexts in the same process - SvelteKit's bundled `+server.ts` routes (via the `$vtt` alias), the Vite dev plugin, and the production `server.js` entry point. Keeping it as plain `@ts-nocheck` JS sidesteps build/type friction across those three load paths. This is the biggest structural deviation from the spec's proposed layout, and it's a direct consequence of merging what the spec imagined as a standalone process into the main app's single server/port (see `vtt/README.md`'s architecture note - the WS server used to be its own Express+ws process and was folded in).

VTT battle-map uploads (`data/vtt-uploads`) are still container-local and are lost on deploy, by choice. Migration 040 (and 050 if the homebrew library has landed) must be applied with `npm run db:migrate:prod` before the deploy is used.

## 9. Known Fragility / Untested Edges

- **Unit tests under `vtt/` are new and thin (2026-11-19):** `vttTokenMove.test.ts` and `vttGridDistance.test.ts` are the first to cover `token:move`; prone adjacency deliberately rounds to whole squares while movement rounds to the foot. Everything below is otherwise still untested.
- **No automated tests** for anything under `vtt/` or `static/vtt-app/`. Repo-wide test coverage is limited to `src/lib/server/services/effects.test.ts` and `src/lib/rules/dnd5e.test.ts` - nothing VTT-related, and `vtt/server/*.js` is `@ts-nocheck` so `svelte-check`/`tsc` don't cover it either. Everything here is verified only by manually walking the milestone checklist in `vtt/README.md`.
- ~~`gmSocketId` is vestigial~~ - **fixed in Phase 2 Section 0b**: a live GM socket now rejects a second claim; a stale one is reclaimable.
- **Client-generated token/marker IDs** with no server-side uniqueness check beyond "is an id present" - `session.tokens[token.id] = token` on `token:add` will silently overwrite an existing token if a colliding or malicious ID is sent. Low risk from a trusted GM client, but worth knowing now that `token:add` authorization has loosened (Phase 2 Section 1a lets a player add their own PC token) - a player could theoretically send a colliding id, though `type`/`ownerId` scoping still limits what they can overwrite to their own tokens in practice.
- ~~No cleanup on socket close~~ - **fixed in Phase 2 Section 0c**: `player:left` broadcasts on disconnect, `connected` flag tracked, `gmSocketId` cleared when the GM leaves.
- **In-memory schema drift across incremental development** - `main.js` defensively does `session.markers = session.markers || {}` on receipt, implying the marker feature landed after some sessions might already be running. Harmless given no persistence (a restart resets everyone to the current schema), but a pattern to watch if any future feature adds required fields to `tokens`/`players`.
- **Unbounded room-code collision loop** (`generateRoomCode`) - `do {...} while (existingSessions.has(code))` has no retry cap. Not a practical concern at a 33-character alphabet × 6 chars for POC-scale usage, but note it before any load-testing.
- **`vtt/README.md` has drifted from the code** - still lists only `join.js`/`token.js`/`map.js` (missing `marker.js`, and now also missing `target.js`), doesn't mention `movement.js`/`markers.js`/`targeting.js`/`shapeGeometry.js`, the token library, the upload pipeline, or any Phase 2 work, in its file tree, and its "Known POC gaps" section incorrectly claims "no zoom/pan" (Section 4). This doc supersedes it; the README should be trimmed down to just the "how to run it" section or updated wholesale next time someone's in there.
- **Phase 2's `TARGET_WINDOW_MS` (5 minutes) is a hand-picked constant** (`vtt/server/handlers/target.js`) with no design rationale beyond "roughly one combat turn's worth of back-and-forth" - if actual play reveals it's too short (slow turns) or too long (stale targets get attacked accidentally), it's a one-line tune, not a redesign.
- **Prepared spells are display-only, not wired to combat resolution** - the mini-sheet lists a character's prepared spells (name + level), but clicking one doesn't do anything; only weapon-style `actions` (with `damageRolls`/`toHitBonus`/`damageBonus`) are wired to the attack-targeting flow. Proper spell damage would need per-spell damage formulas, which don't exist anywhere in the current data model (spells are pulled from `content_definitions`/`character_content_instances` with no damage-expression field) - a real gap if spell-slinging PCs are common at the table, not addressed in this phase.
- **`token:add`'s GM path is still fully unrestricted** - the Phase 2 change only added a narrow *additional* allowance for players (their own `pc` token); a GM can still add a token with any `id`/`ownerId`/`stats` combination, same trust level as the original POC.
- **Cone/cube placement UX is functional but minimal** - a single click-drag sets both facing and length in one gesture; there's no way to adjust cone angle or cube width after arming placement (must cancel and re-open the form to change them), and no snapping to grid angles (45°/90° etc.). Fine for the current scale, a candidate for polish if cone/cube placement turns out to be fiddly in real play.
- ~~Character-sheet pull-through is a one-time snapshot~~ - **superseded**: a 30-second polling resync was added (see changelog below) covering only the reference fields with **no editable control anywhere in the VTT** - at the time this entry was written, that was `ac`, `saves`, `actions`, `preparedSpells`. **Correction (later superseded again):** the mini-sheet AC field became editable in a later pass (see the "Editable AC" changelog entry below), so `ac` was removed from the synced field set at that point - the poll's current field set is `saves`, `actions`, `preparedSpells` only. Everything else that's read-only-on-the-sheet-but-editable-in-the-VTT (`ac`, `hp`, `maxHp`, `speedFt`, all four vision fields) is deliberately excluded from the poll, not just `hp`/`spellSlots` as first scoped - a first pass also synced vision/speed/maxHp and was found (via a real user report) to silently revert a GM's manual in-session override (e.g. temporarily granting darkvision for a spell/potion) back to the sheet's baseline on the next poll tick. The dividing line is "if a human can edit it in the VTT, the poll must never touch it," and that's a property of the data model, not the poll-vs-push transport - a future push-based system (sheet save → VTT) would need the exact same exclusion list, not just faster delivery. See the Phase 2 Follow-Up Priorities below for the push-based direction.
- **`characters.active_vtt_session_id` can go stale with no error surfaced** (Phase 4 Section 1) - it's a plain string, not a foreign key (VTT rooms are in-memory only, wiped on restart, so there's nothing in Postgres for it to reference). A character that joined a session before a server restart still has that room code saved; every roll after the restart just silently logs nowhere, since the write path only checks "is this non-null," not "does this room still exist." Same class of fragility the rest of the VTT already accepts (Section 1 above), just newly inherited by a persisted column rather than only affecting in-memory state.
- **Combat History/PDF export only replays the combat log, never the roll log** (Phase 4 Section 3) - `roll_log_entries` is scoped by VTT room, not by encounter (see Phase 4 Section 1 for why), so there's no query that can say "these specific rolls happened during this specific encounter." A player's Combat History PDF shows attacks/damage/HP changes only; skill checks/saves/initiative rolls made during that same fight aren't included even if they logically belong there.
- **No live two-browser UI click-through for any of Phase 4** - verification was direct HTTP/WS-script checks against the live dev database (migrations, endpoint auth, live-push confirmed via a connected WS test client, list/detail/404 behavior), not a real click through the sheet's Join Session box, the roll dice-icon buttons, the VTT's Start/Stop Combat buttons, or the print/PDF dialog. Per this doc's own established discipline (see the Phase 2.5 "verified" trust-gap notes below), that gap should be closed before calling any of Phase 4's UI verified, not assumed from the endpoint-level checks.
- **`npm run dev` now binds to the network, not just localhost** (Phase 7, bundled into the sounds-and-creature-library commit with no other discussion of it in that commit) - `package.json`'s `dev` script changed from `vite dev` to `vite dev --host`. Combined with the complete absence of WS handshake auth (Section 7 above), anyone on the same local network as the dev machine while it's running can now reach the dev server directly, not just the host machine itself. Likely intentional (testing from a phone/tablet on the same network), but worth confirming with whoever runs this that it's a deliberate tradeoff, not an incidental side effect of an unrelated commit.
- **Phase 7 has no verification record** (see that phase's own section above) - unlike every phase before it, this audit could only reconstruct what shipped by reading the commit diffs, with no session notes on what (if anything) was actually clicked through live. Treat all of Phase 7 as unverified until someone actually plays a session with it.

# Phase 2 - Character Sheet Pull-Through & Combat Actions

Diff against [`.claude/briefs/vtt-phase-2-spec.md`](../.claude/briefs/vtt-phase-2-spec.md), using this doc's numbered sections 1-10 above (the POC) as the baseline. Section numbers below mirror the phase-2 spec's own (0 through 4), not a continuation of 1-10.

## 0. Foundations - ✅ As designed

All three foundation fixes were implemented before any Section 1-4 work, per the spec's explicit sequencing instruction.

**0a. Field-level authorization on `token:stat:update`** - `PLAYER_EDITABLE_FIELDS`/`isFieldEditAllowed(role, isOwner, field)` in `vtt/server/handlers/token.js`, exactly as spec'd, with one deliberate deviation from the spec's own example list: **`hp`/`maxHp` are included** in the player-editable set. The spec's illustrative `GM_ONLY_FIELDS` example listed them as GM-only, but that would have regressed real, already-shipped behavior (`ownTokenListHtml`/`wirePlayerSidebar` in `main.js` already let a player edit their own token's HP - confirmed by reading the code before implementing). A player self-tracking their own HP isn't the "self-buff" risk 0a exists to close; that risk is about *other* fields (`condition`, `defeated`) and about editing *other tokens'* HP, both of which stay blocked. Disallowed writes now get an explicit `token:stat:update:error` back to the sender (`{ tokenId, stat, reason: 'field_not_editable' }`) instead of a silent no-op.

**0b. Single-GM claim enforcement** - `findLiveGmSocket()` in `vtt/server/handlers/join.js` checks `socketsBySession` for a live (`ws.readyState === OPEN`) GM socket before allowing a claim. A second live GM is rejected with `join:error`/`gm_already_claimed`; a stale claim (GM disconnected) falls through to reclaim.

**0c. Disconnect cleanup** - `wsServer.js`'s `ws.on('close', ...)` now looks up the session and, for a departing player, sets `connected: false` on their `session.players` entry and broadcasts `player:left`; for a departing GM whose id matches `session.gmSocketId`, clears it. Player objects gained a `connected` boolean (defaults `true` on join/reconnect).

**A structural bug caught during implementation, not in the spec**: the first pass gated the field-allowlist check entirely behind the pre-existing `canEditToken(meta, token)` ownership check. Since Section 3b's whole point is allowing a write on a token the sender does *not* own (an enemy they've targeted), that ownership gate would have made 3b's exception unreachable once built. Restructured to `(canEditToken(meta, token) && isFieldEditAllowed(...)) || isValidHpTarget(...)` - two parallel authorization paths, not one narrowing the other. Caught by writing the Section 3 verification test before assuming the code was right, not by inspection.

**How to verify**: see the Phase 2 changelog entry below for the exact WS-script test sequence used (join races, disconnect/reconnect, disallowed-field rejection) - all four checks pass against the live dev server.

## 1. Character Sheet Pull-Through - ✅ As designed, 🔁 one major reinterpretation

### 1.0 Shared derived-stat extraction (prerequisite work, not explicitly itemized in the spec)

The spec's Section 2 flagged, as an explicit pre-check: is the math engine "cleanly callable from the VTT's context"? It wasn't. `armorClass`, `initiativeBonus`, `speedFt`, `passiveScore` (generalizing perception/insight/investigation), and a new `visionRadii` were extracted from inline `$derived` formulas in `CharacterSheetForm.svelte` into `src/lib/rules/dnd5e.ts` as plain, narrow, pure functions (same style as the pre-existing `spellSaveDc`/`spellAttackBonus`), callable from both the Svelte component and the new server-side VTT API routes. `equippedAttackItems(inventory)` was similarly extracted from the sheet's inline "battle action items" filter. The component now delegates to these instead of recomputing inline; `combatFormulaHelp`'s tooltip-breakdown text (a second, parallel computation used only for hover text) was left as-is since it already read the shared `computed*` values for its "Total" lines - the actual duplication there is cheap re-derivation of intermediate bonus arrays for display, not a source of possible disagreement.

**Verified two ways**: (1) a direct unit-level script (`tsx`) exercising each extracted function against hand-computed expected values, including the speed formula's exact order of operations (base/set → additive bonuses → chained multipliers → floor/clamp) and the new vision-modifier resolution; (2) `svelte-check` (0 errors) plus an actual character sheet page fetch confirming the SSR'd HTML still shows `Armor Class = 10` with the correct formula breakdown for a fresh level-1 human fighter.

### Vision derivation - 🔁 reinterpreted, not a feat-name lookup table

The spec's Section 1b assumed a small hardcoded feat→vision-field mapping table, using Darkvision as its example. Two things made that the wrong shape for this codebase: Darkvision is a **racial trait**, not a feat, and this codebase has no structured race/trait data at all (confirmed: zero hits for "darkvision" anywhere in the schema, and `character.metadata.race` is freeform text). The actual correction, confirmed with the project owner: per `docs/architecture/modifier-primacy-architecture.md`, Darkvision isn't tied to any specific container type - it's just an ordinary Modifier targeting a vision stat, attached via whatever Container grants it (racial-trait container, feat, item, doesn't matter).

Implemented as such: `visionRadii(modifierSources, context)` resolves `vision.normal_ft`/`vision.dark_ft`/`vision.true_ft`/`vision.devil_ft` through the exact same `resolvedAdditiveModifiers()` machinery already used for AC/speed/etc, additive on top of a standard-human baseline (30/0/0/0). A new migration (`021_vtt_vision_targets.sql`) registers those four target keys in `modifier_targets` with `runtime_supported: true` (verified applied against the dev DB), so they show up properly labeled in `/admin/rules/hooks` immediately. **No feat-name or race-string matching exists anywhere.**

**Deliberately not built in this pass**: actually authoring a "Darkvision (Racial)" Container/Modifier and attaching it to specific characters. That's real campaign content, a DM decision via the existing `/admin/rules/hooks` → `/admin/rules/modifiers` → `/admin/rules/effects` flow (confirmed to already fully support it) plus the character's own owner self-selecting it on their sheet (also an existing, unmodified flow) - not a code gap. Until a DM does this, every character resolves to the 30/0/0/0 baseline, which is correct behavior, not a bug.

### 1a/1b. Character combobox + token pre-population - 🔁 one authorization change the spec didn't explicitly call out

`GET /vtt/api/characters` (minimal list, reuses `listCharacters` unchanged - no portrait field exists anywhere in this codebase, confirmed, so the picker shows name + class/level text only) and `GET /vtt/api/characters/[id]` (full computed snapshot: hp/maxHp, speedFt, vision, ac, saves, actions, spellSlots, preparedSpells - ownership-scoped exactly like `getCharacter()`, confirmed via a cross-account 404 test) both exist under `src/routes/vtt/api/characters/`, following the existing no-manual-auth-check pattern (`hooks.server.ts` already gates the route).

Client: a new "Pick Your Character" modal (`static/vtt-app/main.js`, `#characterPickerModal`), opened via a new **Add My Character…** button in the player sidebar, following the same modal-overlay pattern as the existing image picker. Selecting a character fetches the detail snapshot and builds a `token:add` payload client-side, exactly like the existing manual "Add token" flow already does - just pre-filled from real data instead of blank, plus new fields (`characterId`, `ac`, `saves`, `actions`, `spellSlots`, `preparedSpells`) riding along on the same payload.

**Authorization change, flagged explicitly since the spec's own Section 0 foundations list didn't call it out**: `token:add` was GM-only in the POC. Section 1a's "selecting a character creates their token" flow requires a *player* to create their own token, so `token:add` now also allows `meta.role === 'player' && token.type === 'pc' && token.ownerId === meta.playerId` - GM's own privileges (any type, any owner) are unchanged.

**How to verify**: log in as a user with an existing character (equip a weapon, prepare a spell if a caster), join a VTT session as that player, click **Add My Character…**, confirm the resulting token's HP/speed/vision/AC match the character sheet. Try `token:add` with `type: 'enemy'` from devtools as that player - rejected. Try adding a `pc` token with someone else's id as `ownerId` - rejected. All four checked against the live dev server via a WS+HTTP script; see changelog.

## 2. Mini Character Sheet In-VTT - ✅ As designed, one deliberate scope cut

Renders inline in each owned PC token's card in the player sidebar (`miniSheetHtml()` in `main.js`) - AC (read-only), saves (read-only tags), actions (clickable rows, wired to Section 3's targeting), spell slots (current/max per level with Use/Reset controls sending `token:stat:update` with a whole-array replace), and prepared spells (read-only list). **No new network calls** - everything was already pulled onto the token at creation time (Section 1) and stays in sync via the existing token broadcast plumbing; opening the panel doesn't re-fetch anything. This directly satisfies the spec's "populate once at creation, don't auto-resync" limitation by construction - there's only one pull point, not two.

**Deliberate scope cut vs. the spec's sequencing note**: the spec mentions, without detailing, a "click any token for a details panel" feature reusing the same data. Not built as a separate surface in this pass - the mini-sheet only shows for the player's *own* tokens right now. Low cost to add later (same card markup, read-only mode, driven by whichever token's data is present), deprioritized to keep this pass focused; noted as a follow-up below rather than silently dropped.

**Known limitation surfaced during implementation, not fully solvable without new data**: prepared spells render but aren't wired to the attack-targeting flow (see Known Fragility above) - only weapon-style `actions` are, since only those carry `damageRolls`/`toHitBonus`/`damageBonus`. Spell damage resolution would need a data-model addition (per-spell damage expressions) that doesn't exist yet.

Verified visually via a headless-browser screenshot (Playwright) in addition to the underlying data checks.

## 3. Combat Actions & Targeting - ✅ As designed, plus one leak the spec explicitly warned to check for

### 3a. Target selection

`vtt/server/handlers/target.js` (new) - genuinely the "thin pass-through" the spec asked for: no role/ownership check at all (any joined socket may send it), rebroadcasts `{ sourceTokenId, targetTokenIds }` verbatim, and stashes `lastTargetTokenIds`/`lastTargetAt` on the sender's own `meta` object for 3b to consult. Client: `render/targeting.js`'s `drawTargetRings()`, a dashed ring around each targeted token, wired into `main.js`'s render loop and `handleMessage` switch.

### 3b. Applying results

A player may now write `hp` on a token they don't own if it's present in their own most recent `target:select` within a 5-minute window (`TARGET_WINDOW_MS` in `target.js`) - implemented as `isValidHpTarget()` in `token.js`, a parallel authorization path alongside (not instead of) the existing ownership+field-allowlist check (see the Section 0 structural-bug note above for why this had to be a genuine OR-branch). `defeated`/`condition` remain excluded from `PLAYER_EDITABLE_FIELDS` regardless of targeting, so a player's attack can lower an enemy's HP but never itself flags a kill - matching both this spec and the original POC spec's "GM decides death on their own timeline" rule.

**A genuine leak the spec explicitly flagged as "worth a manual check, not an assumption" - found and fixed, not just re-verified.** `broadcastToken()`'s `extra` payload (`{ tokenId, stat, value }`) was shared verbatim across all recipients. Even though the enclosed `token` object was correctly filtered (`stats` stripped for enemy/npc), the *top-level* `value` field - e.g. an enemy's new HP after a hit - rode along unfiltered to every player. This was dormant in the POC (only the GM could ever trigger a `stat:update` on an enemy token, and the GM already sees real values), but became live and exploitable the moment Section 3b let players trigger it. Fixed by making `broadcastToken`'s `extra` accept a per-recipient function, omitting `value` for non-GM recipients on enemy/npc stat fields; client-side, `token:stat:update`'s handler now guards `msg.value !== undefined` before applying anything.

This surfaced a second, related design gap not explicit in the spec: **an attacking player never receives an enemy's HP at all, so they can't compute a new absolute value the way the GM's direct HP input does.** `token:stat:update` gained an optional `delta` field (used only via the `isValidHpTarget` path) - the server computes `Math.max(0, currentHp + delta)` server-side, so the player only ever says "this hits for 8," never learning the number before or after. `value` (absolute set) is unchanged for every other case (GM editing directly, a player editing their own HP).

Damage was originally rolled **client-side** (a small standalone `rollDamageDice()` in `main.js`, since the vanilla client can't import `$lib/rules/dnd5e` - no build step, no `$lib` alias resolution). **Superseded in Phase 2.5** (see the Phase 2.5 section and changelog below): both to-hit and damage now roll **server-side** via `POST /vtt/api/characters/[id]/roll-attack`, reusing the exact `rollAttack()` the character sheet uses, so the VTT shows the full advantage/disadvantage-pool + extra-dice + crit breakdown instead of a flat `XdY+Z`. The client still applies the resulting damage via the same `token:stat:update` `delta` path described here.

**How to verify**: with a player-created PC token (weapon equipped) and a GM-added enemy token, click a weapon action in the mini-sheet, click the enemy on the map - confirm a target ring renders in all tabs, the attack fires, the enemy's HP visibly drops in the GM's view. Explicitly re-checked (not assumed) via a headless-browser test: inspected the attacking player's own rendered "other tokens" panel post-attack and confirmed no real HP number ever appears, only "No status known" (or a GM-set `condition` if present). Confirmed a player cannot write an enemy's `hp` without a recent `target:select` on that token.

## 4. AoE Shape Types - ✅ As designed

`vtt/server/handlers/marker.js`'s `marker:add` now trusts `input.shape` from a fixed allowlist (`circle`, `cone`, `cube`, `sphere`) instead of hardcoding `'circle'`, and carries the new geometry fields (`angleDeg`, `lengthFt`, `widthFt`, `coneAngleDeg`) through opaquely - the server stays fully geometry-agnostic, exactly as the existing circle-only code's own comment anticipated ("shape is on the data already so cone/line/cube can be added as new branches here later without touching the sync/visibility plumbing" - that comment turned out to be accurate).

**4a/4b.** New standalone `static/vtt-app/render/shapeGeometry.js` - `isPointInShape()`/`getTokensInShape()`, covering circle/sphere (identical distance-check math, sphere is a semantic alias per spec's "cheapest shape to add" framing), cone (angle + distance test from an origin point), and cube (point-in-rotated-rectangle, anchored at the near-edge midpoint - the same anchor convention as a cone's origin, so the placement UI works identically for both). `render/markers.js` dispatches per-shape draw functions instead of the old single circle-only branch.

**4c.** Placement UI extends the existing "arm placement mode" banner pattern: circle/sphere keep the original single-click placement; cone/cube start a drag on mousedown (origin), live-preview the shape during `mousemove` (reusing `drawMarkers()` directly with a synthetic in-progress marker - no separate preview-rendering code needed), and confirm on `mouseup` with the drag's angle/distance converted to `angleDeg`/`lengthFt` (rounded to the nearest 5ft). The marker-controls form (shape select + radius vs. width/cone-angle fields) was factored into one shared `markerFormHtml()`/`wireMarkerForm()` pair used by both the GM and player sidebars, rather than duplicating the new shape UI in four places.

**Auto-targeting (spec 4b's second bullet)**: implemented as a shared `placeMarker()` helper - every shape placement (not just cone/cube) computes `getTokensInShape()` against the placed marker and sends `target:select` for whatever it catches, wiring Sections 3a and 4 together exactly as the spec anticipated ("removes the need to manually multi-select targets for an AoE").

**Cosmetic bug caught during verification, fixed**: the sidebar's marker-list entries showed "0 ft" for cone/cube markers (the label logic only ever read `radiusFt`, which directional shapes don't set). Fixed with a small `markerSizeLabel()` helper covering all three size conventions.

**How to verify**: place a cone and a cube near a cluster of enemy tokens (drag to aim, release to confirm) - confirm the rendered shape's orientation matches the drag direction, confirm tokens caught inside get auto-highlighted with target rings, confirm tokens outside are not targeted. Verified visually via headless-browser screenshots showing a 90° cone correctly catching two of three placed enemies (and excluding the third, positioned outside the cone's arc) with visible target rings on the caught tokens, plus a cube rendering correctly oriented along its drag direction.

# Phase 2.5 - Fix Attack Flow (server-side shared roll)

Diff against [`.claude/briefs/vtt-phase-2.5-attack-flow-fix-spec.md`](../.claude/briefs/vtt-phase-2.5-attack-flow-fix-spec.md).

## 0. Diagnosis - 🔁 root cause was upstream of the click plumbing

The reported "clicking does nothing at all" was **not** a broken click handler or dropped event. A full read of the arm→click→resolve path found the wiring correct and the app initialising cleanly (so no load-time exception). The actual cause, confirmed with the user against a live session: the player's mini-sheet showed **"No equipped weapons"** - there was literally no action row to click. The VTT's Actions list is built from `equippedAttackItems()` (items with `location === 'equipped'`/`equipped === true`), so a weapon sitting un-equipped in inventory produces no action. This also answered a parallel user question ("I've not seen anything about inventory") - the mini-sheet only surfaces *equipped attack items* as clickable rows, never a full inventory list. Once a weapon was equipped, the original flow did fire.

The prior "verified" claim for this path (Phase 2 Section 3) came from a headless test that exercised the data/event layer, not a real two-client UI click-through - the specific trust gap this spec was written to close.

## 1. Explicit Attack flow + shared server-side roll - ✅ built (live verification pending)

Rather than patch the flat client-side roll, the flow was rebuilt per the spec's Section 1, and the roll logic was unified so the VTT and the character sheet can't diverge:

- **Shared roll module** - `src/lib/rules/attackRoll.ts` (new): `rollAttack()`, `rollWithModifiers()`, `rollDamage()`, `battleDamageBonuses()`, `damageCandidatesFor()`, extracted **verbatim** from `CharacterSheetForm.svelte`'s `rollBattleAction`/`rollText`/`rollDamageExpression` (which now delegate to it - no sheet behaviour change; the component keeps thin wrappers that pass its own reactive `modifierSources`/`classRows`/ability scores/RNG). One roll implementation, two callers.
- **Server endpoint** - `POST /vtt/api/characters/[id]/roll-attack` (new): ownership-scoped like the sibling GET route, loads the **live** character, matches the clicked action to a real equipped inventory item by name, and runs `rollAttack()` against the character's full `modifierSources`. This is the only place the rich roll can happen - the vanilla VTT client can't import `$lib`, and the token only carries a *flattened* action (`toHitBonus`/`damageBonus`/`damageRolls`), not the modifier graph that drives advantage/disadvantage/Bless/crit.
- **Rebuilt client flow** (`static/vtt-app/main.js`, `index.html`, `style.css`): arm (banner names the weapon + valid targets get a yellow highlight ring) → click a target → **confirm card with an explicit Attack button** (no more instant resolve) → on Attack, call the endpoint → render the *exact same* to-hit + damage breakdown the sheet shows → apply damage via the existing `token:stat:update` `delta` path. Hit/miss is decided client-side **only when this client is allowed to know the target's AC** (own/PC token, or GM); for a hidden-AC enemy it shows the to-hit total and leaves the hit call to human adjudication rather than fabricating or leaking AC. On a determined miss, no damage event is sent.

**Known limitation carried forward**: conditions set *in the VTT* (`token.conditions`, e.g. flipping Poisoned on a token) are not wired into the character's `modifierSources`, so the roll reflects the sheet's persistent effects, not VTT-transient ones. Bridging that is a real follow-up, not part of this fix.

**Verification status** - ⚠️ **automated only so far; live two-browser check still owed.** Passing: `svelte-check` (0/0), a deterministic parity test proving `rollAttack()` reproduces the sheet's "Pokey Sword" (Poisoned + Bless) breakdown byte-for-byte, dev server boots clean, endpoint registers and is auth-gated. **Not yet done**: the actual GM+player live click-through the spec (and this doc's own hard-won lesson) require before this is called "verified." Section 3 of the spec - repointing Phase 3 Section 2a at this flow - is deliberately deferred until that live check passes.

### 2026-07-14 - Dim/dark brightness bands were backwards for darkvision (user-caught)
User question: "why does dim light show darkvision range in grey, and dark light show vision range in color + darkvision range in grey - shouldn't it be the other way around?" Correct on inspection - this traced to the original POC spec's own text, which explicitly allowed "dim: everyone gets grayscale, no color band" as a simplification, without noting that it inverts 5e RAW's actual darkvision rule: *"you can see in dim light... as if it were bright light, and in darkness as if it were dim light. You can't discern color in darkness, only shades of gray"* (PHB). Per RAW, a darkvision creature should get **full color** in dim light (dim = bright, for them) and only **grayscale** in true darkness - the POC's simplified version gave the opposite (zero color in dim, some color in dark), making `dark` accidentally better than `dim` for a darkvision creature when it should be the reverse.

Fixed in `render/vision.js`'s `getTokenVisionRadii()`: `dim` mode's `colorRadius` now scales with `visionDarkFt` (0 if no darkvision, full color out to darkvision range if the token has it) instead of being hardcoded to 0; `dark` mode is unchanged (already RAW-correct: color within normal vision, grayscale beyond via darkvision, matching the "darkness never restores color" rule). Verified two ways: a direct unit-level check of `getTokenVisionRadii()` confirming the exact radii for darkvision/no-darkvision tokens across all three brightness modes (including an explicit "dim gives more color than dark" severity check), and a visual headless-browser test against a real four-color test map, screenshotted in all three brightness modes - `bright` shows color to 30ft, `dim` now shows full color all the way to 60ft (previously would have shown zero color), `dark` shows color to 30ft with grayscale from 30-60ft (unchanged).

### 2026-07-14 - Bright light no longer capped at the token's short indoor vision radius
Follow-up to the same conversation as the dim/dark fix above. User observation: unaided daylight sight isn't capped at a fixed distance in reality (or in 5e RAW) - only darkvision has a defined range - so treating `bright` mode's reveal radius as the same ~30ft `visionNormalFt` used for indoor/dark scenes made outdoor daylight maps feel far more fog-of-war-constrained than the scenario calls for.

Added a `BRIGHT_LIGHT_RADIUS_FT = 150` constant in `render/vision.js`; `bright` mode's `colorRadius` is now `Math.max(normalFt, 150) * pxPerFoot` instead of just `normalFt * pxPerFoot` - a floor, not a replacement, so a token with an unusually large `visionNormalFt` (e.g. from a future homebrew effect) still gets its own larger value rather than being clamped down to 150. `dim` and `dark` are untouched - the token-specific radius is still the meaningful constraint in both, which is exactly where vision *should* matter. Verified via a direct unit-level check (`getTokenVisionRadii` returns 1500px/150ft for a standard 30ft-normal-vision token in bright light, confirmed the 150ft floor doesn't clamp down a token whose own `visionNormalFt` already exceeds it, and confirmed `dim`/`dark` results are unchanged).

150ft is a flat, un-derived number - picked as "large enough to feel like daylight, small enough to still be a number" rather than computed from any rule. Worth revisiting if actual play shows it's too small (very large outdoor maps) or unnecessary (if fog-of-war for bright scenes turns out not to matter enough to warrant a floor at all, vs. just fully unbounded/whole-map reveal).

### 2026-07-14 - Standard 5e status conditions (Poisoned, Prone, etc.)
User request: a way to track the standard 5e status conditions on tokens, via a modal with checkboxes.

Added as a genuinely new field, not an extension of the existing one - `token.conditions` (a plural array, e.g. `['poisoned', 'prone']`) is entirely separate from the pre-existing singular `token.condition` (the GM's coarse "healthy"/"bloodied"/"critical" HP-severity signal). Visibility: conditions are treated as observable battlefield state, not secret like HP - `filterTokenForPlayer` already only strips `stats` from enemy/npc tokens (confirmed by reading `vtt/server/store.js`), so the new field passes through unfiltered for every token type with no server-side change needed. Editing follows the existing ownership rule: `conditions` was added to `PLAYER_EDITABLE_FIELDS` in `vtt/server/handlers/token.js` (a player can toggle conditions on their own token - "I just got poisoned by a trap" is the same self-service pattern as tracking their own HP) and to `TOKEN_LEVEL_STAT_FIELDS` in both the server and client (a top-level token field, not nested under the free-form `stats` bucket).

Client: a new `conditionsModal` (`static/vtt-app/index.html`) with checkboxes for the 14 standard 5e conditions (Blinded, Charmed, Deafened, Exhaustion, Frightened, Grappled, Incapacitated, Invisible, Paralyzed, Petrified, Poisoned, Prone, Restrained, Stunned, Unconscious - hardcoded list, not configurable, matching POC scope), generated dynamically rather than hand-written per checkbox. A "Conditions…" button was added to both the GM's token card (any token) and a player's own token card (their own only), opening the same modal; saving sends one `token:stat:update` with the full checked array. A small `conditionTagsHtml()` helper renders the active list as read-only tags, reused in the GM card, the player's own card, and the "Other tokens in view" list (all three contexts, since none of them are secret).

Canvas: `drawTokens()` in `render/tokens.js` gained `drawConditionsRow()` - a compact row of 3-letter abbreviations (e.g. "POI PRO") drawn above the token, positioned above the HP bar/health-condition badge so it can coexist with either.

Verified via headless browser: GM sets Poisoned + Prone on a hidden-stats enemy token, confirms both tags show on the GM's card and the canvas renders "POI PRO"; confirms a player (whose session never receives that enemy's `stats`) still sees "Poisoned Prone" in their "Other tokens in view" list, proving the new field isn't accidentally being stripped alongside `stats`; confirms a player can independently set a condition on their own token via the same modal.

### 2026-07-15 - Editable AC on all tokens, server-side hit/miss with AC discovery, DM manual attacks
User follow-up to the Phase 2.5 attack flow, three interlocking asks: (1) AC on all tokens, editable - player AC derived at creation but then player-editable; (2) the DM able to run the same attack flow for enemy/NPC tokens; (3) enemy AC hidden from players but *discoverable through play*.

- **Editable AC**: the player mini-sheet AC field is now editable (was read-only) and `ac` was removed from the 30-second resync poll's field set - it now has an in-VTT editable control, so polling it would revert a manual change on the next tick (superseded for sheet-driven changes on 2026-11-23: a manual edit is still never reverted, but the token now also moves by the size of later sheet AC changes, see `sheetAc` at the bottom; the exact clobber the vision/speed fields hit before; the poll's exclusion rule is "if a human can edit it in the VTT, the poll must never touch it"). The GM's Add Token form and each GM token card gained an AC input. True AC lives top-level (`token.ac`) for both PCs and enemies; `filterTokenForPlayer` now strips `ac` (alongside `stats`) for enemy/npc tokens, and `token:stat:update` treats `ac` as a sensitive field for enemy/npc so its value never rides out on the event either.
- **Server-side hit/miss + AC discovery** (new `attack:resolve` WS event, handled in `vtt/server/handlers/token.js`): the client rolls to-hit/damage (shared module, as before) but no longer decides hit/miss - it sends the roll to the server, which alone knows the target's hidden AC. The server computes hit (crit auto-hits, fumble auto-misses, no-AC-set auto-hits), applies damage on a hit, and replies with an `attack:result` carrying only hit/miss + the *rolled* damage (never the capped applied amount, which would leak exact remaining HP on an overkill, and never the AC). AC discovery: on a hit that genuinely cleared AC, the server records the *lowest* such roll as the token's `knownAc` and broadcasts it to everyone - rendered under the token as `AC ≤ X`, a bound players tighten through play (swing 16 and hit → shows 16; later swing 14 and hit → shows 14). A crit that auto-hit below AC deliberately does **not** update the bound. `knownAc` is top-level so it survives the player filter, distinct from the stripped true `ac`. **Manual known AC (2026-11-19):** a dedicated `token:knownAc:set` event (any role, any visible token, value 0-99 or `null` to clear) lets a player (Other tokens in view) or the GM (Token Manager) note a bound by hand via the Known AC modal. The handler never reads the real AC, so it can't act as an oracle. Attack log lines now also carry the to-hit total, e.g. `hits (17)`, `(natural 1)` on a fumble.
- **DM manual stat-block attacks**: since enemies aren't full characters, each GM token card has a small attacks editor (name + to-hit + damage dice, stored in the token's `actions` array). Clicking a row arms the same targeting/confirm/roll/resolve flow a player's weapon uses; the roll goes through a new `POST /vtt/api/roll-manual` (reusing a new `rollManualAttack()` in the shared module - a plain `d20 + toHit` / `damage` roll with no modifier graph, same result shape and display as a character attack). `resolveAttack()` picks the character endpoint when the source token has a `characterId`, the manual endpoint otherwise.

**Verification: automated only, live check still owed** (same discipline as the Phase 2.5 entry above). `svelte-check` 0/0 across 440 files, all vanilla-JS files pass `node --check`, dev server boots clean. **Not yet exercised live**: GM sets an enemy AC → player attacks and cannot see the AC, only discovers `AC ≤ X` on a hit; a miss reveals nothing; the DM adds a manual attack on an enemy token and attacks a PC; the AC-discovery bound tightens correctly across several hits. Handed to the user for the two-browser click-through - still outstanding as of the 2026-07-15 infra fixes below (those fixes made the *deploy* reachable/current; they did not exercise this feature's actual click-through).

### 2026-07-15 - Production infra: stale-deploy edge caching, and large map uploads silently rejected
Two separate production-only bugs, both hit while the user tried to live-verify the attack-flow work above - neither is a VTT logic bug, both are `server.js`/hosting-layer issues that happened to surface at the same time.

1. **Deploys weren't showing up.** Diagnosed by fetching the deployed `main.js` two ways: the plain URL returned a stale 2026-07-14 build (missing even Phase 2 features), while `main.js?v=<random>` returned the current 2026-07-15 build - proof the origin had the right file and a URL-keyed edge cache (Railway fronts requests with Cloudflare, which caches `.js`/`.css` by extension) was serving a stale copy. Root cause: `static/vtt-app/*` (`index.html`, `main.js`, `style.css`, `render/*.js`) are plain, unhashed filenames that never change between deploys, served with no `Cache-Control` header - unlike SvelteKit's own hashed `/_app/immutable` assets, which are safe to cache forever precisely because their names *do* change per build. Fixed in `server.js` by setting `Cache-Control: no-cache` on every `/vtt-app` request, forcing revalidation on each load. **User confirmed fixed after deploying.**
2. **Large map/token image uploads silently failed** (a 230KB image uploaded fine, a 3.12MB map did not) despite the upload route's own 15MB limit. Root cause: `@sveltejs/adapter-node` caps every request body at `BODY_SIZE_LIMIT` (default 512KB, read once at module load) and rejects anything larger *before* it reaches the route - a production-only ceiling (`vite dev` has no such cap, which is why the same large map "always worked" in local testing). Fixed in `server.js` by setting `process.env.BODY_SIZE_LIMIT = '20M'` before dynamically importing the handler module (must happen pre-import, since the limit is read once at that module's top level). **User confirmed fixed after deploying.**

Both fixes live in the same `server.js`, committed separately (`1e96fb3`, `d3b17d2`) since they're independent root causes that happened to be diagnosed back-to-back. No VTT feature code changed in either fix.

# Phase 3 - Magic

## 0. Close-out - ✅ confirmed by user before this phase started

Spec's Section 0 asked for a live two-browser click-through of the Phase 2.5 attack flow before any Phase 3 work. User confirmed this had already been done; Phase 3 proceeded directly on top of it.

## Research finding that reshaped the plan - the spell system was already far more built than the spec assumed

Before writing any code, a full audit found `content_definitions`/`spell_definitions`/`character_content_instances`/`character_spell_slots` already real and working, with a complete prepare → know → cast flow (`castCharacterSpell`, `src/lib/server/services/catalogue.ts`) that validates known+prepared, lets the player choose which slot to spend (including upcasting), and runs `on_cast`/`on_use` Action steps. The actual gap was narrow: `spell_definitions` had zero damage/attack fields, and the Action-step `damage` step type only ever applied to the caster's own HP or produced a text-only readout - there was no code path anywhere that applied damage to a *different* character/token. That's the one piece this phase added.

## 1. Spell damage/scaling data model - ✅ built

New migration `022_spell_damage_model.sql` extends `spell_definitions` (not `modifier_targets` - confirmed during research this needed its own structured shape, not a scalar dot-notation target) with `resolution_type` (attack/save/auto), `damage_type`, `base_dice`, `save_ability`, `save_effect` (half/negate), and `scaling_json` (cantrip `{kind, extraDice, tiers}` or leveled `{kind, extraDicePerSlotLevel}`). `src/lib/types/content.ts`'s `ContentDefinition.spell` and `CharacterContentInstance.spellDamage` carry the same shape.

**A structural requirement surfaced mid-planning, not in the original spec**: the user flagged that feats/items modifying spell damage are planned (an item intended to double a specific spell's dice already exists in play). This meant `resolveSpellDamage()` couldn't be a closed calculation over just a spell's own baseline - it had to consult the character's Modifier sources through the same dot-notation mechanism weapon damage already uses. Addressed by layering candidate targets `damage_roll.spell.all` → `damage_roll.spell.<damageType>` → `damage_roll.spell.<name-slug>` (mirroring `damage_roll.weapon` → `damage_roll.weapon.<ability>`), and by giving `modifier_type='multiplier'` a dice-pool-specific interpretation in this resolver ("repeat the resolved dice expression N times") distinct from `speedFt()`'s scalar-multiply use of the same type. Authoring "doubles a spell's dice" needs **no new admin UI** - it's an ordinary Modifier attached via the existing `/admin/rules/hooks` (register the ad-hoc target once) → `/admin/rules/modifiers` → the granting item's own "Attach Modifier" tab flow.

## 2. `resolveSpellDamage()` - ✅ built, unit tested

`src/lib/rules/dnd5e.ts` - pure function alongside `spellSaveDc`/`spellAttackBonus`. Resolves baseline + scaling first (cantrip tiers crossed at character level; leveled spells' extra dice per slot level cast above minimum), then folds in modifier-sourced `extra_die`/`bonus`/`penalty`/`multiplier` Modifiers matching the layered candidate targets. Unit tests in `dnd5e.test.ts` cover cantrip scaling at levels 1/5/11/17, leveled upcast scaling, and the doubling-multiplier case.

## 3. Admin authoring UI - ✅ built

`/admin/magic` (`ContentTypeAdmin.svelte` + `content-admin.ts`) already had a full generic spell editor (level/school/casting time/etc.) reusing the same machinery as items - extended with a Damage sub-section (Resolution/Damage Type/Base Dice, conditional Save Ability+Effect, Scaling kind + its two field pairs), following the exact pattern the item block already used for its own damage fields.

## 4. Server: roll-spell endpoint - ✅ built

`POST /vtt/api/characters/[id]/roll-spell`, modeled on `roll-attack`. Reuses `castCharacterSpell()` **unchanged** for known/prepared validation and slot spend (including upcast choice) - one slot-spend implementation, not two. Layers on: a spell attack roll (for `resolution:'attack'`, via the same two-phase to-hit → outcomes → damage-modifier pattern `rollAttack()` uses for weapons) and `resolveSpellDamage()` for the damage roll, returning a breakdown shaped like `AttackRollResult` plus `resolution`/`damageType`/`saveDc`/`saveAbility`/`saveEffect`.

## 5. Server: applying spell damage - ✅ built

Attack-resolution spells reuse the existing `attack:resolve` WS event **unchanged** - a spell attack roll vs. AC is mechanically identical to a weapon attack once you have a to-hit total, so no server changes were needed for that branch. A new `spell:resolve` event (`vtt/server/handlers/token.js`, registered in `wsServer.js`) handles save/auto spells: same target-window/GM authorization gate as `attack:resolve`, but the pass/fail comparison itself happens client-side (a caster's own Spell Save DC isn't secret, unlike a target's AC) - the server's job here is purely "is this HP write authorized," applying full damage on `auto` or a failed save, half/none on a successful save per the spell's `save_effect`.

## 6. VTT mini-sheet: from display-only to castable - ✅ built

The old flat, inert "Prepared spells" list (`data-spell-name`, no click handler - confirmed dead in the pre-Phase-3 audit) is gone. Selecting a spell arms targeting exactly like a weapon action (`armActionTargeting`/`openAttackConfirm`/`resolveAttack` in `main.js` were generalized to branch on `action.kind`, not forked into a parallel pipeline). For save spells, the confirm modal shows the spell's DC (openly, since it's not secret) plus the spec's "lightweight type-in-the-target's-save-result" prompt; for auto spells, a single Apply-Damage confirm. `preparedSpells` gained an `id` field (the `character_content_instances` id) so the client can address a specific prepared spell without relying on name uniqueness - already covered by the existing `PLAYER_EDITABLE_FIELDS`/`TOKEN_LEVEL_STAT_FIELDS` allowlists since it rides on the same whole-array field.

Per the spec, kept deliberately light - the sheet has no token/target concept. ### 2026-07-15 - Phase 3: magic system implemented (damage model, casting flow, admin authoring, starter spells)

# Phase 4 - Combat/Roll Logging & Encounter History

Not diffed against a written spec brief - no `.claude/briefs/` file exists for this phase. Built directly from conversation with the project owner, across three successive rounds in one session, each starting from "what do you think" and narrowed down via clarifying questions before writing any code (see each section's "design forks" note below for what was actually asked and decided, not just what shipped).

## 0. Combat Log (VTT + character sheet) - ✅ built, live-push verified, UI click-through not yet done

A running, human-readable log of damage/HP events ("Aurora hits Goblin 1 for 8 piercing damage."), persisted in Postgres so it survives a VTT restart - unlike the rest of session state, this was a hard requirement, not an accepted POC gap.

**Data model**: new `combat_log_entries` (migration `024_combat_log.sql`) - `id`, `encounter_id` (FK to the pre-existing, previously VTT-unconnected `encounters` table from the initiative-tracker feature), `message`, `details` jsonb, `created_at`.

**Design forks resolved with the user**: (1) VTT sessions had zero DB linkage before this - rather than force the GM through the existing `/encounters` initiative-tracker UI to get an `encounter_id`, the VTT gained its own **Start Combat**/**Stop Combat** buttons (`POST /vtt/api/session/[id]/combat`) that silently create/close an `encounters` row behind the scenes, displaying the resulting ID to the whole table. (2) The `vtt/server` ws process (`token.js`) needed a way to persist rows but can't import `$lib/server/services/*.ts` directly (same reason it stays plain `@ts-nocheck` JS - see Section 6 above) - it calls a new internal `POST /vtt/api/log` over loopback HTTP instead, authenticated by a shared-secret header (`x-vtt-internal-secret`, env `VTT_INTERNAL_SECRET`) rather than a session cookie, since there is none. (3) A real bug this surfaced: `hooks.server.ts`'s blanket "redirect to /login if no session" gate would have blocked that internal call before it ever reached the route - fixed with a narrow path-specific exemption for `/vtt/api/log` (the GET side still requires a normal session, checked in-route since the hook no longer enforces it for that path).

**Write paths**: `vtt/server/handlers/token.js`'s `attack:resolve`/`spell:resolve` cases build a log line right after applying damage (attacker name resolved from `session.tokens[msg.sourceTokenId]`, not `meta.playerName`, so a GM-controlled monster's attack attributes correctly too) and POST it. On the character-sheet side, `updateCharacter()` (`characters.ts`) now reads the character's HP *before* `replaceResources` overwrites it, diffs against the submitted value, and - only if the character has joined an active encounter (`getActiveEncounterForCharacter`) - logs "X takes N damage."/"X heals N HP." Both paths funnel into the same `logCombatEvent()` (`combatLog.ts`).

**Join Combat**: a small "encounter ID + Join" control on the character sheet, gated on the existing `is_active` flag; deliberately a *separate* function from the GM-facing `addEncounterParticipant` (that one requires the same user to own both the encounter and the character - fine for a GM building their own initiative order, wrong for a cross-user player join), so a new `joinEncounterAsCharacter()` was added instead.

**Display**: a live-updating panel in the VTT sidebar (fed by a new `combat:log` ws broadcast) and a polling panel on the character sheet (`GET /vtt/api/log?encounterId=&afterId=`, ~4s interval - the sheet has no live transport of its own, Socket.IO is still just a stub per `src/lib/server/realtime.ts`).

## 1. Roll Log (separate table, scoped to the VTT room - not the encounter) - ✅ built, live-push verified, UI click-through not yet done

A second, distinct log for ordinary d20 rolls - skill checks, ability checks, saves, initiative - e.g. "Draegorn rolled a 21 on Intimidation." with a `[?]` revealing the full breakdown ("d20 15, +4 proficiency, +2 Charisma").

**Design fork, corrected mid-plan by the user**: the first pass reused `combat_log_entries`, gated the same way as HP-delta logging ("must have joined an active encounter"). The user caught this was wrong before any code was written: *"We are not likely to have encounter IDs for non-combat rolls"* - most rolls (skill checks, roleplay saves) happen with no combat active at all. Rescoped to the **VTT room** instead: a room exists the moment the GM opens the VTT, well before Start Combat, so rolls log for the whole time the party is connected, not just during fights. Since VTT rooms are in-memory only (no DB row to foreign-key against), this needed its own new table and its own join step, not a variant of the encounter flow:

- New migration `025_roll_log.sql`: `characters.active_vtt_session_id` (plain nullable `text`, no FK - see the Known Fragility note above for the consequence) + `roll_log_entries` (`session_id text`, not `encounter_id uuid`).
- New "Join Session" control on the character sheet (separate from "Join Combat"), validating the pasted room code against the live in-memory `sessions` Map (`$vtt/store.js`) rather than any DB table.
- `logRoll()`/`getCharacterVttSessionId()` (`rollLog.ts`) - the write path already knows the exact room id (whatever the character joined), so it broadcasts `roll:log` directly rather than scanning for a match the way the combat log has to.

**Scope decision, confirmed with the user**: only single, deliberate d20 rolls are logged - one skill check, one ability check, one save, initiative - wired into `rollSingleSkillCheck`/`rollSingleSavingThrow`/`rollAbilityCheck`/`rollInitiative` in `CharacterSheetForm.svelte`. The sheet's "Roll All Skills"/"Roll All Saves" reference buttons (18/6 lines at once, meant for glancing at all options, not a real in-fiction roll) are deliberately never logged.

**No new roll-computation code was needed** - `rollWithModifiers()` (`src/lib/rules/attackRoll.ts`) already returns `{ text, natural, total }`, a full source-attributed breakdown per modifier-primacy §2.6/§3.3; this phase only pipes that already-computed value into the new log. The `[?]` on the character sheet reuses the existing `simpleRollResult` modal verbatim (just populated from a past log entry's stored `details` instead of a live roll); the VTT's own Roll Log panel uses a native `<details>/<summary>` per line for the same affordance, with zero new JS state.

## 2. Small correctness fix: combat log live-push consistency

Noticed while building Section 1's live-push (`logRoll` broadcasting directly to its room): the combat log's own live-push was one-sided. `token.js` broadcast its own `combat:log` line after its internal POST resolved, but sheet-originated writes (HP-delta edits) had no live push at all - a GM watching the map wouldn't see a player's HP change until their sheet's own next poll happened to catch up, or the GM refreshed. Fixed by moving the broadcast into `logCombatEvent()` itself (`combatLog.ts` now imports `sessions`/`broadcast` from `$vtt/store.js` and scans for any session with a matching `encounterId`), and removing the now-redundant broadcast from `token.js` (it would otherwise double-broadcast every VTT-originated line). Both logs now push live consistently, from either origin.

## 3. Combat History + PDF export - ✅ built, live-push/list/404 verified, print dialog not yet clicked through

**UI entry point superseded by Phase 5 Section 1** - this section's own "Combat History" button/modal (`EncounterHistoryList.svelte`) was folded into the unified Activity Log modal's Combat tab and no longer exists as its own component; everything below about the underlying data/route is still current, only the trigger and list markup moved.

Gap identified: the combat log panel only ever showed while `activeEncounterId` was set (character joined to a *currently active* encounter). The moment the GM clicked Stop Combat, the panel disappeared and the log became UI-unreachable, even though the rows are still sitting in Postgres.

**Design forks resolved with the user**: (1) scoped **per-character** (mirrors the existing Version History pattern - a button on that character's own sheet - rather than one combined view across everything a player owns). (2) PDF export uses **browser print-to-PDF** (`window.print()` + `@media print` CSS hiding `.topbar` and the download button itself), not a new PDF-rendering library - there was no PDF code anywhere in the repo before this, and `docs/project-handover.md` §2.30/4.16 explicitly flags PDF export as planned-but-undecided and warns against over-investing given it's a secondary feature.

**New**: `listEncountersForCharacter()`/`isCharacterInEncounter()`/`getEncounter()` (`encounters.ts`, unchanged, still current); ~~`EncounterHistoryList.svelte`~~ (deleted in Phase 5 - its list markup, "View" links and all, now lives directly in `CharacterSheetForm.svelte`'s Activity Log modal); a route `src/routes/characters/[id]/encounters/[encounterId]/` (unchanged) that re-checks character ownership (`getCharacter`, same 404-if-not-yours gate as every other character route) *and* that this specific character actually participated in that specific encounter (404 otherwise, catching a stale/mistyped URL rather than silently showing an unrelated fight).

**Known scope limit, stated explicitly rather than silently accepted**: only replays `combat_log_entries` - roll-log entries aren't included, since rolls are scoped by VTT room (Section 1) and there's no query that can currently say "these rolls happened during this specific encounter."

## Verification status across all of Phase 4

Real HTTP/WS-level checks against the live dev database (Neon), using the existing `tony@test.com`/`Newton` test fixtures - not a live two-browser UI click-through of any of the three pieces above. That pass is still owed before any of Phase 4 is called UI-verified.

# Phase 5 - Session Notes & Activity Log UI Consolidation

Not diffed against a written spec brief, same as Phase 4. Two rounds in the same session: a new feature (Session Notes), followed immediately by a UI cleanup pass once the user saw how cluttered the character sheet had gotten from three rounds of bolting a panel on per feature (combat log, roll log, session notes, each with their own inline join box).

## 0. Session Notes (separate table, scoped to a persisted Game Session - not the VTT room, not an encounter) - ✅ built, live-push verified, UI click-through not yet done

A third, distinct log - free-form out-of-character table talk, not damage or dice: `Tony: We went shopping` / `FaeRunner: ...and bought a shiny new sword!`. Explicitly *not* full collaborative document editing (the user called that "ideal but not needed") - just an append-only, type-and-Enter feed, same shape as the other two logs.

**Naming fork, decided upfront rather than discovered mid-build**: "session" was already double-booked in this codebase - a real `sessions` table already exists for HTTP auth sessions (`001_initial.sql`), and "VTT session" already means the in-memory room object (`vtt/server/store.js`, Section 1 above). The new persisted entity here is called a **Game Session** everywhere in code and UI (table `game_sessions`, service `gameSessions.ts`) specifically to avoid a third collision.

**Design forks resolved with the user, each a real fork from how the other two logs work**:
- **Attribution is to the signed-in player, not a character.** Out-of-character chatter isn't something a specific character "said," and a player without any character sheet open should still be able to post. Concretely: `game_session_notes.user_id` is a real FK column (unlike the other two logs, which bake a name into the message text) - a `users` row is always available to join against at read time, so a later display-name change is reflected correctly instead of frozen into old rows.
- **Postable from both the VTT and the character sheet**, same dual-surface posture as the combat log. Turned out simpler than the combat log's version of this: posting a note is always a plain, already-authenticated browser `fetch()` - unlike `token.js`, `vtt/server`'s ws process never needs to *originate* a note itself, so there's no internal-secret/loopback-HTTP bridge, and neither `wsServer.js`'s dispatch nor any `handlers/*.js` file needed a change (no new *client-to-server* ws message type was introduced - the client only ever receives). `vtt/server/store.js` did gain one small addition: `createSession()`'s session shape now includes `gameSessionId: null` alongside the pre-existing `encounterId: null`, set/cleared by the new Start/End Session route exactly like the combat one already does. The service function that inserts a note (`logSessionNote`, via `gameSessions.ts`'s `broadcastToMatchingSession`) pushes it live to any VTT room whose `session.gameSessionId` matches - the same scan-`sessions.values()`-for-a-match pattern `combatLog.ts`'s `logCombatEvent` already uses, not the roll log's simpler direct-broadcast (the roll log's write path always knows the exact room it's posting into; a note posted without any specific room in scope, only a Game Session id, has to scan the same way the combat log does). The VTT client only ever *receives* `game_session:note`, never sends one.
- **Reviewable history, not ephemeral like the roll log.** The user explicitly chose this over reusing the room-code approach: notes need to outlive the VTT room they were posted from (rooms are in-memory, wiped on restart), so a Game Session is a real, named, persisted row - `game_sessions` (`owner_user_id`, `name`, `is_active`) - not just a reused room code. New migration `026_session_notes.sql` also adds `users.active_game_session_id` (at the time, the user-level equivalent of `characters.active_vtt_session_id` from the roll log - "which Game Session is this player currently posting into"; **superseded by Phase 6 Section 0**, which moves the room join itself to `users` too and narrows what this column is actually for - see there for the current picture).

> **Superseded by Phase 6, flagged rather than silently left wrong**: the rest of this section (the "Join Session Notes" box below, and Section 1's description of per-tab join boxes) described the *original* three-separate-IDs join model. Phase 6 replaced it with one "Join Room" box covering all three logs, and deleted the `/sessions` list page entirely. Kept below for the historical record of what was built in this round; read Phase 6 for what's actually there now.

**Deliberately simplified**: no `game_session_participants` table - "which sessions has this user been part of" (for the `/sessions` history list) is inferred (`owner_user_id = $1 OR exists a note from $1`) rather than tracked via an explicit join event. Costs "joined but never posted" not showing up in history; acceptable for a running log, not a roster.

**Surfaces**: GM gets **Start Session**/**End Session** buttons in the VTT (`POST /vtt/api/session/[id]/game-session`, mirrors `.../combat/+server.ts` exactly - creates/closes a `game_sessions` row, stores the id on the live room object); both roles get a message box + live panel in the VTT sidebar. The character sheet gets a "Join Session Notes" box (pastes the Game Session id, sets `users.active_game_session_id`) and, once joined, a message box + live panel. A new global nav item, **Sessions** (`/sessions` list + `/sessions/[id]` detail/post page, same shape as `/encounters`) - global rather than per-character, since attribution and the join state are both user-scoped, not character-scoped.

# Phase 6 - Room-Code Unification & Live-State Bug Fixes

Not diffed against a written spec brief, same as Phases 4-5. Prompted by the user actually using what Phase 5 shipped: a real ECONNREFUSED hit during live testing, then *"I've lost all of the ability to add a session - could we also simplify everything and just use the Room code for all 3 logs?"* Everything in this phase either directly answers that, or was caught by the user's own manual click-through testing immediately after - the first real UI testing this feature area has had, and it found real bugs none of the earlier HTTP/WS-script verification could have caught.

## 0. Room-Code Unification - ✅ built, live-derivation verified end-to-end

Before this, joining combat/rolls/session-notes each needed a *different* id: an Encounter ID (Start Combat), the Room Code (roll log's own "Join Session"), and a Game Session ID (Start Session). Three things to obtain from the GM and paste into three different boxes, for state that all lives in the same VTT room anyway.

**Design, confirmed with the user (two options presented, "one code to type, history still kept" chosen over fully collapsing the data model)**: keep the persisted `encounters`/`game_sessions` records (so Combat History and Session Notes history keep working), but stop requiring a separate join per feature - typing the Room Code once now auto-attaches whichever encounter/game-session is *currently* active for that room, derived live rather than joined explicitly.

- **The room join moved from `characters.active_vtt_session_id` to `users.active_vtt_session_id`** (migration `027_unify_room_join.sql`, with a data-carry-forward `UPDATE ... FROM` for existing joins) - one join per *player*, not per character, so every character sheet a user opens reflects the same room without re-joining per character.
- **`getActiveEncounterForCharacter`** (`encounters.ts`) now derives purely from that room join - character's owner's `active_vtt_session_id` → that room's live `session.encounterId` (`$vtt/store.js`) - with **no separate "Join Combat" click required**. It can't go stale the old explicit-join model could (join before combat starts, and the old design needed a re-click once it did) - verified directly: joined a room, *then* started combat in it, and the character auto-attached with zero explicit join call. Combat History still needs a real `encounter_participants` row to list a character's past fights, so this function lazily upserts one the first time it resolves a live encounter for a character - same end state the old explicit join produced, just automatic.
- **`joinEncounterAsCharacter` deleted outright** - no longer called from anywhere, not left as dead code.
- The character sheet's `joinSession` action (room join, previously roll-log-only) became the **one** join action, `joinRoom`, writing `users.active_vtt_session_id`. `joinCombat`/`joinGameSession` actions deleted.
- **VTT sidebar simplified to match**: players no longer need to copy an Encounter ID or Game Session ID off the map (they already have the Room Code from joining the VTT itself) - `combatControlHtml()`/`sessionNotesControlHtml()` now show plain status text ("Combat is active in this room") instead of an ID-to-paste line.
- **Explicit "Leave Room"**, added after a follow-up report: the room join is plain persisted account state, deliberately surviving logout/login (so a reconnecting player doesn't have to re-join) - but that also meant it never expired on its own, and the user found themselves permanently reconnected to a stale room (`BKY2DY`) from earlier testing purely by logging back in as the same account. ## 2. Two live-state bugs, both caught by the user's first real click-through - ✅ fixed, re-verified

The first actual UI testing this whole feature area had (everything through Phase 5 was HTTP/WS-script-verified only, flagged explicitly each time as not yet click-through-tested). Both bugs were things no synthetic API check would have surfaced, because they're both about what happens to *already-rendered* state over time, not about a single request/response being correct in isolation.

**Bug A - combat not appearing on the character sheet even though the VTT showed it live.** Root cause: `activeEncounterId`/`activeGameSessionId`/`activeVttSessionId` were only ever computed once, at `load()` (SSR) time - a documented, accepted limitation since Phase 4 ("if a player has the sheet open and the GM starts combat afterward, the sheet won't show it until they reload"), which the user's own testing pattern (open the sheet, *then* start combat in the VTT) hit directly. Fixed with a new `GET /vtt/api/characters/[id]/activity-status` endpoint and a background poll (4s interval, runs for the lifetime of the character sheet component) that refreshes local `liveEncounterId`/`liveGameSessionId` state independently of the page's original `load()` snapshot. Verified directly: joined a room, confirmed no combat active, started combat in that room *after* joining, and confirmed the poll picked it up with no page reload.

**Bug B - Session Notes tab showing an unrelated, stale session ("Bumaer") instead of the currently-joined room's.** A genuine design flaw in Phase 5's `getActiveGameSessionForUser`, not staleness: it was a fallback chain (prefer the room-derived session, else fall back to the older explicit `users.active_game_session_id` column from `joinGameSession`) - but that fallback column never expires, and the character sheet was using this *same* fallback-carrying function for "what's active in my room," so any session ever manually joined via `SessionNotesModal`'s own Join button would permanently shadow the correct "nothing active in this room" answer whenever the room-derived value came back null. Split into two functions: **`getRoomGameSessionId`** (pure room-derivation, no fallback - what the character sheet's `load()` and `postSessionNote` now use exclusively) and **`getActiveGameSessionForUser`** (keeps the fallback, but now scoped narrowly to `SessionNotesModal`'s own "have I joined *this specific* session" check, where a fallback genuinely belongs). Verified directly: manually set a stale `active_game_session_id` unrelated to the current room, confirmed the character sheet's derivation correctly ignored it (`null`), and confirmed the modal's own per-session join check still correctly honored it for the session it was actually about.

## 3. Small fixes alongside the above

- **ECONNREFUSED on the internal combat-log callback** (`vtt/server/wsServer.js`) - the very first thing hit during this round's live testing, before any of the above. `internalApiBaseUrl()` hardcoded the literal `127.0.0.1` for `token.js`'s loopback call to `/vtt/api/log`; on the user's Windows setup, Node's dev server was listening on the IPv6 loopback (`::1`), which `localhost` resolves correctly but a hardcoded IPv4 literal can't reach at all - `ECONNREFUSED` despite the server genuinely being up. Fixed by using `localhost` instead of `127.0.0.1`, letting Node's own resolution do the same fallback the browser already relies on. Requires a dev-server restart to take effect (this file loads at Vite-plugin/startup level, not through SvelteKit's hot-reload graph) - flagged to the user rather than assumed picked up automatically.
- **CSS/layout cleanup**, from a screenshot showing "Leave Room" visually cramped into a 24×24px circle: `.formula-help-button` (a fixed-size circular "?" icon button) had been reused for text-labeled buttons ("Leave Room", "Full log") it was never sized for. Both switched to `.text-button`, which was extended to also style `<a>` tags (previously `button`-only). `.combat-encounter-id` gained actual layout CSS (it had none at all before - was falling back to unstyled block rendering). Room-code inputs were inheriting a global `input { width: 100% }` with nothing to override it for a 6-character string - added a `.room-code-input { width: 10ch }` class.

# Phase 7 - Soundscape, Creature Library & Stability Fixes

Not diffed against a written spec brief, same as Phases 4-6 - built directly in three commits (`a671daf4`, `7bee96a2`, `8fdad208`) with no accompanying planning conversation captured in this doc. **This section was written retrospectively, from reading the commit diffs alone** (this pass had no access to whatever live back-and-forth with the user actually happened) - unlike every phase above, none of the "confirmed with the user" / "user reported" framing below should be read as independently verified conversation history, only as inferred from code comments the implementer left in place at the time. Treat this section as a structural description of what shipped, not a verification record.

## 0. Combat log: flavor phrasing + a damage-reporting consistency fix - ✅ built

`vtt/server/handlers/token.js` gained `MISS_PHRASES`/`CRITICAL_HIT_PHRASES` pools (`pickLine()` picks one at random per event) so the combat log reads as prose rather than a flat ticker - a miss now logs its own line (previously misses logged nothing at all), and a critical hit gets distinct "epic" phrasing instead of the plain hit sentence. Ordinary hits are otherwise unchanged in shape.

**Consistency fix bundled in the same commit**: the hit-line log message switched from reporting `damageApplied` (the HP-capped amount actually removed) to `damage` (the raw rolled amount) - matching the reasoning `attack:result`'s own payload already used (Phase 2 Section 3b): showing the capped amount would leak an enemy's exact remaining HP whenever overkill trims a big roll down to a small number (roll 10, 3 applied → "hits for 3" tells the whole table only 3 HP was left). The log line was the one place this had drifted from that rule.

## 1. Ambient/battle music, per-attack creature sound cues, GM soundboard - ✅ built

Extends a pre-existing ambient-music feature (`map.musicUrl`, a bundled/custom track picker per map) that was never previously itemized in this doc - `vtt/server/musicLibrary.js` indexes `assets/music/` (26 bundled tracks) and was already there before this phase.

- **Battle track**: a map can now also carry `battleMusicUrl`. `effectiveMusicUrl()` (`main.js`) prefers it over the regular ambient track whenever `session.encounterId` is set (i.e. combat is active via the Phase 4 Start/Stop Combat buttons), swapping back the instant combat ends. No server-side change needed - this is a pure client read of state the server already broadcasts (`combat:state`, `map:set`).
- **Crossfade engine**: two `<audio>` elements (`ambientAudioA`/`ambientAudioB`) ping-pong which one is "active" on every track swap, so a swap fades the outgoing track down while fading the incoming one up over the same 600ms window rather than a fade-to-silence-then-back gap. **A real bug fixed while building this, per the code's own comment, not a separate report**: an earlier version of the fade-cancellation logic used a counter token checked only the next time a `requestAnimationFrame` loop happened to tick - if the tab was backgrounded (browsers throttle/stop rAF while hidden), that check could never fire, leaving the old track playing forever and, in one attempted follow-on fix, permanently wedging every future music update behind a promise that could no longer resolve (**"Set Map stopped working entirely after that fix"**, per the comment). Replaced with a fade controller that's cancelled synchronously and directly the instant a newer fade starts, independent of whether the old rAF loop is still ticking.
- **Volume**: a numeric input was added alongside the existing slider (they mirror each other); one-shot sound effects (hit cues, creature roars, soundboard clips) now share that same volume level via `oneShotEffectVolume()`, rather than always playing at full volume regardless of the music level the GM has set.
- **Per-token creature sound cues**: tokens gained a GM-only `soundFolder` field (Add Token form + token card dropdown, `TOKEN_LEVEL_STAT_FIELDS`/GM-only per `PLAYER_EDITABLE_FIELDS`) pointing at a folder under the new `assets/creature-sounds/<folder>/` (one bundled example pack shipped, `dragons/`, ~170 clips across 15 sub-categories like ROAR/BREATHING/DEATH, indexed recursively including subfolders by the new `vtt/server/creatureSoundLibrary.js`, mirroring `tokenLibrary.js`'s own recursive-walk shape). Whenever that token's `attack:resolve` or `spell:resolve` fires - hit or miss, since a creature's attack cue should play regardless of whether the swing connects - the server picks a random clip from its folder and broadcasts it as `fx:play`'s new `creatureSoundUrl` field; every connected client plays it as a one-shot `Audio()` at the shared effect-volume level. Served via new routes `GET /vtt/api/creature-sounds` (folder list) and `GET /vtt/api/creature-sounds/[folder]/[...rest]` (a clip, `[...rest]` rather than a single `[filename]` segment specifically so subfolder-nested clips resolve).
- **GM Soundboard**: a new modal (one button per creature-sound folder) for triggering a random clip from any folder on demand, independent of any attack - new `soundboard:play` WS event (`vtt/server/handlers/soundboard.js`, GM-only, registered in `wsServer.js`), reusing the exact same `fx:play`/`creatureSoundUrl` broadcast shape the automatic per-attack cue uses.
- **Incidental fix**: `musicLibrary.js`'s `resolveMusicLibraryPath` had a restrictive filename-character allowlist that legitimately rejected real track titles containing parens/spaces (e.g. `"Battle Against Unseen Forces (Calm Ver).ogg"` 400'd). Replaced with the same resolved-path-prefix traversal guard `creatureSoundLibrary.js` uses for its own path resolution (reject anything that resolves outside the bundled root, rather than restricting which characters a filename may contain).

## 2. Creature template library ("Save as Template") - ✅ built

New `creature_templates` table (migration `028_creature_templates.sql`, owner-scoped to the saving GM's own account - "a small trusted group may have more than one GM, each with their own creature library," per the migration's own comment) plus `src/lib/server/services/creatureTemplates.ts` (`listCreatureTemplates`/`createCreatureTemplate`/`deleteCreatureTemplate`) and routes `GET`/`POST /vtt/api/creature-templates` + `DELETE /vtt/api/creature-templates/[id]`, following the same plain-authenticated-browser-route posture as `creature-templates`' sibling VTT routes (no internal-secret bridge needed - only ever called from an already-logged-in browser).

Client: a "Save as Template…" button on each GM token card snapshots the token's reusable fields only - `type`/`ac`/`stats.hp`/`stats.maxHp`/vision/`speedFt`/`imageUrl`/`soundFolder`/`actions` - deliberately excluding `id`/`x`/`y`/`hidden`/`ownerId`, which are per-instance placement details, not part of what makes a saved "goblin" a goblin. A new **Creature Library** modal lists saved templates (with per-card Delete) and prefills the Add Token form on selection, so a recurring monster doesn't need to be rebuilt by hand every session.

## 3. Bug fixes bundled in one commit ("Fixed some bugs") - ✅ fixed

Three unrelated real bugs, fixed together:

- **Attack rolls 404'd when a GM rolled on behalf of a token they don't own.** `POST /vtt/api/characters/[id]/roll-attack` called the owner-scoped `getCharacter(userId, characterId)` - correct for the character's own player, but a 404 for anyone else, including the GM. Since a GM may need to roll a weapon attack for a player's token (player stepped away, etc.), and *who* is allowed to trigger a given token's attack in the first place is already enforced at the VTT socket layer (`attack:resolve`), this ownership check was redundant at best and a hard blocker at worst. Fixed with a new `getCharacterForRoll(characterId)` in `characters.ts` - the same computed character detail, deliberately un-scoped by owner, used **only** for this read-only roll endpoint; every state-mutating character route (spell-slot spend, etc.) keeps its existing, stricter owner check unchanged. Matches this app's stated product philosophy ("campaign members can view/interact with all campaign sheets, no ownership locks").
  - A related client-side fallback was added in the same pass: if `roll-attack` fails with `item_not_found` (the action was added directly to a PC token via the GM's own "add attack" form rather than being a real equipped item on that character's sheet - `roll-attack` always re-derives from the live sheet, so there's nothing there to match), the client now falls back to the flat `roll-manual` path instead of hitting a dead end - losing the sheet's rich advantage/disadvantage-aware roll, which a homebrew ad-hoc attack was never going to have anyway.
- **Tokens could be dragged off the visible map and become permanently unreachable.** A fast drag past the map's edge (easy while zoomed out, since drag tracking runs at window level) could commit a `token:move` outside `[0, widthPx] x [0, heightPx]`; once there, the token renders off-canvas and the cursor can never map back to on-canvas coordinates to hit-test it again. Fixed with a new `clampToMapBounds()` applied to every token drag/drop commit point (mouse and touch alike) - not applied to marker/shape placement, which stays reachable via its sidebar list regardless of position. A **"Recenter on Map"** button was also added to every token card (GM and player) as a rescue for any token already stuck off-canvas from before this fix shipped, sending a plain `token:move` to the map's center.
- **A full sidebar re-render on every token move was resetting whatever else the viewer had open elsewhere in the sidebar** - reported case: a player's marker color picker getting reset mid-edit whenever *any* other player's token moved anywhere on the map, since `token:move`'s handler called a blanket `renderSidebar()` regardless of whose token moved. Fixed by replacing that with a new `updateOtherTokensInViewList()` that only refreshes the `#otherTokenList` div's innerHTML (pure display markup, nothing to re-wire) - `renderSidebar()` itself is now reserved for changes that actually need the whole sidebar rebuilt.

### 2026-07-30 - Map rendering rearchitected to layered DOM/SVG; video/animated map backgrounds

Implements [`.claude/briefs/vtt-map-rendering-rearchitecture-spec.md`](../.claude/briefs/vtt-map-rendering-rearchitecture-spec.md) in full. The map is no longer drawn into the canvas at all - it's a stack of DOM layers behind a now-transparent canvas, which keeps everything interactive (tokens, markers, drag ghosts, rings, all pointer handling) exactly as before.

**Spec Section 0 audit findings** (all six confirmed against code before any rendering change):
1. Canvas drawers besides the map: movement ranges, markers, tokens, target rings, armed-target highlights, shape-drag preview, token-drag ghost + distance line, and the no-map placeholder text - all still canvas-drawn, unchanged.
2. GM manual fog painting: does not exist anywhere (`fog:reveal`/`fog:hide` were never built - confirmed again), so no fog layer decision was needed.
3. Pan/zoom: zoom was applied to the canvas element directly (`canvas.style.width/height`), pan is `#mapWrap` scroll - *not* a shared transformed wrapper. Resolved by adding `#mapStage` (position: relative, sized by the in-flow canvas) so absolutely-positioned layers track the canvas, with `#mapLayers` carrying zoom as `transform: scale()` at the map's native size. Critically, `setZoom()` already calls `render()`, so one `updateMapLayers()` call per render keeps canvas and layers in lockstep with no separate zoom hook.
4. Canvas is the sole pointer surface (all mouse/touch handlers bind to it) - every new layer is `pointer-events: none`, canvas lifted above them via `position: relative; z-index: 1`.
5. Map-switch lifecycle: `getImage()`'s never-evicting Image cache stays for *token* art only; the map now goes through `ensureMedia()` in `mapLayers.js` - swap-on-URL-change only (an unchanged map never restarts a playing video), and outgoing videos are explicitly paused + src-cleared + removed, since a detached or display:none video keeps decoding (the slow-leak the spec called out).
6. SVG clip-path support on the actual tablets: cannot be confirmed from code - explicitly part of the owed live verification below.

**What was built**:
- `render/mapLayers.js` (NEW): black backdrop / grayscale layer (CSS `filter`, clipped to `#vttGrayClip`) / color layer (clipped to `#vttColorClip`) / render-nothing SVG defs, all behind the canvas inside the new `#mapStage`. Clip circles are one SVG `<circle>` per owned token per band, reusing existing circle elements on update (a token move is attribute writes, not element churn). Union-of-circles comes free from the SVG spec. All brightness/darkvision/truesight logic stays in `getTokenVisionRadii()` untouched - by the time radii reach the layer manager, "bright" mode is just `grayRadius === colorRadius`, so the gray layer drops out (and is torn down, not hidden, to avoid double video decode). GM: single unclipped color layer, no gray layer, no clip geometry; `#222` backdrop preserves the old no-image fallback fill.
- Video maps: inferred from URL extension (`.mp4`/`.webm`/`.m4v`/`.ogv` - `isVideoUrl()`), no new map field; `map.imageUrl` stays a plain string. Videos are always `muted` (deliberate policy: any embedded audio is inert by design - sidesteps both the un-gestured-autoplay block and the fact that the ambient-music system has zero awareness of other audio sources), `loop`, `playsInline`. - Upload endpoint: new `video` form field, `.mp4/.webm/.m4v/.ogv` allowlist, 50MB cap; a video with an unrecognized extension is rejected outright (400) rather than saved extensionless, since extension drives both `isVideoUrl()` and the GET route's content-type. GM map form accepts image or video, pulls dimensions from `videoWidth/videoHeight` via a throwaway muted element, and skips the `<img>` thumb for videos.
- Serving route: rewritten from whole-file `fs.readFile` buffering to streaming (`createReadStream` → web stream) with single-range HTTP Range/206 support (`bytes=a-b`, `bytes=a-`, `bytes=-n`; malformed/multi-range deliberately falls through to a full 200 per RFC 9110; out-of-bounds → 416) plus `accept-ranges` - `<video>` seeking/progressive playback needs this. Images unchanged in behavior, now streamed too.
- `server.js`: `BODY_SIZE_LIMIT` default 20M → 60M, clearing the new 50MB video cap **and** fixing the pre-existing mismatch where audio's advertised 25MB cap silently failed between 20-25MB (flagged in the pre-work investigation).

**Perf rationale** (why this, not "extend the canvas draw"): the old player render drew the full map image once per vision circle per pass (N tokens → up to 2N full-map `drawImage`s with a grayscale filter) at native map resolution - tolerable event-driven, unaffordable per-frame once maps animate. Now the browser compositor does all per-frame work (a video map animates with zero JS render loop; the event-driven `render()` cadence is unchanged), and layer count is constant regardless of token count.

**Verification: automated only - live click-through owed, especially on the tablets.** `node --check` on all touched vanilla JS, `svelte-check` 485 files / 0 errors, and a live dev-server HTTP pass against the real routes (throwaway account + uploads, cleaned up after): video upload 200 → full GET 200 with `accept-ranges` and byte-exact body → `bytes=100-299` 206 with correct `content-range`/body → open-ended and suffix ranges 206 → out-of-bounds 416 → bad-extension video 400 → image upload/serve regression-checked. **Not yet exercised**: any actual browser rendering of the new layers (vision bands, union, pan/zoom lockstep, video playback/loop/switch-away cleanup, late-join autoplay, GM view, and all of it on the XPPen + other tablet per the spec's Section 6/verification list - SVG clip-path on those devices is explicitly unconfirmed). Per this doc's own established discipline, treat the rendering half as unverified until that click-through happens; the upload/serving half has real HTTP-level verification behind it.

**Known deliberate tradeoffs**: two `<video>` elements decode the same file when a gray band exists (player with darkvision) - independent decodes, not frame-locked; ambient loops don't need tight sync (same stance as the spec's reconnect ruling), but battery cost on tablets is real and part of what live verification should watch. A gray band reappearing after being absent restarts its video from 0 mid-loop for the same reason. Extensionless external video URLs won't be detected as video (`isVideoUrl` is extension-based); in-app uploads always keep their extension.

### 2026-09-28 - db-traffic-reduction Phase 5: sheet push instead of poll

Every periodic HTTP poll a character sheet tab used to run (roll log / combat log / session notes every 4s, activity-status every 10s) is gone, replaced by push over the same `/vtt-ws` socket the VTT already uses. Full design/measurements in `~/.claude/plans/dndchar/db-traffic-reduction/db-traffic-reduction.md`'s Phase 5 results section; summary here for anyone reading this doc without that plan to hand.

**Transport (`vtt/server/store.js`, `wsServer.js`):** a second, unauthenticated subscription kind alongside a real session `join` - a client sends `{type:'watch', topics}` (topics like `"room:<sessionId>"` or `"game-session:<id>"`, max 10, validated by regex) and gets a narrow slice of events pushed to it without ever joining a session. `broadcast()` auto-forwards `combat:state`/`combat:log`/`roll:log`/`game_session:state` to `room:<sessionId>` watchers (built with a synthetic `{role:'watcher', playerId:null}` recipient, so a GM-only payload is filtered out exactly like a real player socket would be); `game_session:note` is published to `"game-session:<id>"` directly instead (`gameSessions.ts`'s `logSessionNote`), since a note can be posted from a surface with no VTT room in scope at all. `combat:log`/`roll:log` broadcasts now also carry the full DB `entry` (id + createdAt), not just message/details, so a pushed subscriber can merge it straight in without a round trip. A 30s ping/pong heartbeat (`wsServer.js`) terminates dead sockets; a watcher-only socket (no other VTT traffic to notice a drop from) also gets an app-level `{type:'hb'}` frame.

**Sheet side (`src/lib/stores/liveUpdates.ts`, new - replaces the `websocketStore.ts` Socket.IO stub and `visiblePoll.ts`, both deleted):** one shared websocket per tab. `subscribeTopic(topic, {onMessage, onResync})` is a plain function (not a Svelte store) returning an unsubscribe function, dropped into a component's `$effect` the same shape `pollWhileVisible` used to be. On every (re)connect it resends the full watch list and calls every subscriber's `onResync`, which does an incremental (afterId) re-fetch - Postgres stays authoritative, per CLAUDE.md, and there is no poll fallback. Reconnect backoff is 1s→30s; a tab becoming visible again reconnects immediately rather than waiting out the backoff; a 75s no-message watchdog forces a reconnect for a proxy-dropped socket neither side noticed. `mergeLogEntries(existing, incoming, cap)` dedupes by id and sorts by createdAt.

`CharacterSheetForm.svelte` and `SessionNotesModal.svelte` both moved onto this: the room-topic subscription's `onResync` re-derives `liveEncounterId`/`liveGameSessionId` via the existing `activity-status` endpoint (unchanged, still does its participant-upsert) plus an afterId catch-up fetch of both logs; `combat:state`/`game_session:state` pushes also trigger that same re-derive; `combat:log`/`roll:log` pushes merge directly. A `liveEncounterId` change (not the room subscription itself) is what clears and fully re-fetches the combat log, same as before. Session notes use their own `"game-session:<id>"` topic, independent of room membership - `SessionNotesModal` (shared by the sheet, `/sessions/[id]`, and formerly `/sessions`) now works identically whether or not the viewer is connected to any VTT room. No character-sheet field data (HP, inventory, etc.) is ever pushed or auto-refreshed by this work - only the log/activity panels - so there is no unsaved-edit clobber risk to guard against here.

**Verified:** `npm run check` / `npx vitest run` (new `mergeLogEntries` tests plus a `store.js` watch/publish/broadcast-forwarding test using fake sockets); manually against the local dev DB with `DB_QUERY_STATS=1` and a `ws` script standing in for a browser tab - a watcher subscribed to `room:<sessionId>` received `combat:state`/`combat:log` (with `entry`)/`roll:log` (with `entry`)/`game_session:state` pushes correctly, and none of it required being in a live VTT room for `game-session:<id>` note pushes; a 60s idle window with two such watchers connected (one in a room, one on a bare game-session topic) logged `0 queries, 0 rows, ~0.0 KB`. ### 2026-11-21 - Damage taken: damage_taken.* modifiers now apply when damage lands on a PC

- **What.** `src/lib/rules/damageTaken.ts` (`resolveDamageTaken(modifierSources, { amount, damageType, context })`) is the pure resolver. Targets: `damage_taken.all` plus `damage_taken.<type>` when the type is known; untyped damage only matches `.all`. Modifier types: `bonus` = extra damage taken, `penalty` = flat reduction (no new type added), `resistance` / `vulnerability` / `immunity` (value ignored). Order: flat adjustments, floor at 0, then resistance/vulnerability as binary net cancellation per type bucket (resistance halves rounding down, vulnerability doubles, several resistances do not stack, one of each cancels), immunity gives 0. Returns `final`, `steps` and a `breakdown` line such as "7 - 2 (Plate) = 5; halved (Rage: resistance to slashing) = 2". Filtering reuses the shared helpers; `matchingModifiers` was extracted from `resolvedNumericModifiers` in `dnd5e.ts` (same behaviour) because resistance modifiers carry no number and `resolvedNumericModifiers` drops zero-valued ones. Status flags work as everywhere: `flag:half_cover` on the defender's armour is checked against the defender's own effects.
- **Where it applies.** `attack:resolve` and the damage branch of `spell:resolve` in `vtt/server/handlers/token.js`, only when the target token is `type: 'pc'` with a `characterId` (enemy/npc tokens are untouched, which also keeps their resistances out of the table-wide log). The handler can't load a character, so it calls the new internal `POST /vtt/api/damage-taken` (shared-secret header, read-only, exempted from the login gate in `hooks.server.ts` like `/vtt/api/log`), which loads the character with `getCharacterForRoll` and runs the resolver. The lookup is awaited before any HP is read or written, and a failed lookup applies the damage unreduced (logged). `handleTokenEvent` is therefore async; `wsServer.js` catches rejections. Spell saves halve first, then damage_taken applies. Heals are unchanged. Manual HP edits (`token:stat:update` hp) are not damage resolution and are left alone; there is no sheet path that applies incoming damage.
- **Damage type.** The spell's real type (`damageLabel`, lower-cased) when there is one, else the physical type guessed from the weapon's name by the client's existing `inferDamageType` (weapons carry no damage type in the data). The sound bucket `magic` counts as untyped.
- **Audit trail.** The attacker's `attack:result` / `spell:result` carry `damage` (after reduction), `damageRolled` and `breakdown` for a PC target (a PC's HP is already public), shown as a small note under the verdict. The combat log line reports the damage taken and appends "(rolled 7; ...)"; log details gain `damageRolled` and `damageTaken` steps.
- **Also fixed.** `spell:resolve`'s verdict referenced an undefined `damageApplied` (ReferenceError after the HP write, so save/auto spell results never reached the caster); it now sends the damage dealt.
- **Admin.** The modifier admin label list (now `rules-admin.ts`'s `operationRegistry`; the old `modifier-admin.ts` was deleted in the container migration) gained `damage_taken.all` and the other 5e types. The modifier target picker is DB-driven (`modifier_targets`), so `damage_taken.all` and the non-physical types have to be created once in the Rule Hook Builder (Damage Taken namespace). Existing `damage_taken.*` rows are still flagged `runtime_supported = false` (admin shows "not calculated"); flipping that needs a migration, not done.
- **Not covered.** Token conditions (`token.conditions`, e.g. a Half Cover set only on the VTT token) do not raise flags here: only the sheet's active effects do. Tests: `damageTaken.test.ts` (resolver), `vttDamageTaken.test.ts` (resolve level).
- **Review follow-ups (same day).** The VTT shared secret is now checked by `src/lib/server/internalSecret.ts` (constant-time compare) in `/vtt/api/log`, `/vtt/api/roll-log` and `/vtt/api/damage-taken`. With `VTT_INTERNAL_SECRET` unset in production, `damage-taken` refuses (401, logged once, damage then lands unreduced) and the two log routes keep working on the public dev fallback with a one-time warning: set `VTT_INTERNAL_SECRET` on the host. The loopback lookup has a 3 s timeout and the handler bails if the token or room vanished during the await. The route only honours a character that belongs at the table: in a campaign room its `campaign_id` must match the room's, in a Quick room the token's `ownerId` must be the character's owner (otherwise no reduction). Responses carry only `final`, `steps`, `breakdown`. A `damage_taken.all` modifier is described as "resistance to all damage".
- **Extension: immunity.** The spec only asked for resistance and vulnerability (binary net cancellation); `immunity` on `damage_taken.*` is an addition of this work: it sets the damage to 0 and trumps everything else, including vulnerability.

### 2026-11-23 - Token AC follows the sheet by delta (decks unit 5b)
Changes the older "ac never follows the sheet" rule above (the 2026-09-26 AC entry and the character-resync clobber rule): token AC now follows the sheet's *changes*, never its absolute value. Accepted behaviour change: it follows ANY change to the sheet's resolved AC (deck effects, their expiry or undo, equipping armour or a shield, Shield the spell, rests, restores, a hard AC override).
- **`token.sheetAc`** is the sheet AC a PC token last followed. Server-owned: token.js refuses it from `token:stat:update` and `token:update`, `token:add` drops any client copy and never seeds it from the token's own AC (a GM-typed AC would snap to the sheet on the first follow), and it is not in `PLAYER_EDITABLE_FIELDS`. Clients only display it.
- **`src/lib/server/vttTokenAc.ts`**: `followSheetAc(ids)` loads the resolved AC once per character that has a live PC token (none means no database work) and moves `token.ac` by `newAc - sheetAc` (clamped 0..99), clears `knownAc`, and sends `token:stat:update` for `ac`, `knownAc` and `sheetAc` (a hidden token or an unrevealed map reaches the GM only). A token with no baseline just records one (no move). Work is serialised per character, so overlapping loads cannot apply out of order. A GM's manual token AC edit changes `ac` but not `sheetAc`, so it stays as an offset.
- **Trigger**: `emitRealtimeEvent` schedules `followSheetAc` with a 500 ms trailing debounce per character when a live PC token matches. `primeSheetAc` (baseline only) runs before a deck draw; `announceDeck` awaits `followSheetAc` directly for characters with an effect line so the token has moved before the toast.
- **Gap closed**: the encounters page's `advanceEncounterTurn` now returns the characters whose effects it ticked and the action emits `round:advanced` for each, so encounter-driven expiry reaches tokens (and `character:changed`) too.
- **Baseline on add**: token.js fire-and-forgets `POST /vtt/api/token-ac-prime` ({roomId, tokenId}, shared-secret loopback like damage-taken) after a PC token is added. The route reads the character from the live token, checks it belongs at the table (campaign room: same campaign; Quick room: same owner; a forged characterId therefore never gets a baseline) and records the real sheet AC as `sheetAc` without touching `ac`. Rooms are memory-only, so there is no restore path to prime. Known limitation: any token still unprimed (the prime failed, or the change came first) just records its baseline on the first follow without moving, so that one change is not applied to it. Clamping `ac` at 0/99 while `sheetAc` keeps moving can lose an offset at the extremes (accepted).

#### Next round (units 9-10, waits for Ready in unit 12)
- **`POST /vtt/api/session/[id]/next-round`** (room GM only) takes `{ action }`: `request` (default), `start` or `cancel`. Logic is in `src/lib/server/vttNextRound.ts`; the pure state is `vtt/server/roundState.js`.
- **Waiting.** `request` opens `session.roundPending` (in memory on the room; a restart drops it). It waits for the **expected** players: connected player sockets, in a campaign room, whose user owns (`token.ownerId`) a token that has a character. If nobody is expected it processes at once. A second request answers 409 `already_pending`; 409 `too_soon` still guards a double click (running, or inside 2 s of the last one).
- **Ready and Hold on.** `POST .../next-round/ready` with `{ action: 'ready' | 'hold' }`, over HTTP like forage and cost approval (identity is `locals.user`, never the body; 409 `not_expected` for anyone not waited on). Hold clears Ready and Ready clears Hold. When every expected player is ready, the round processes.
- **Start now / Cancel** are GM actions on the same route. Start processes whatever the state; Cancel processes nothing and sends `round:cancelled` to the GM and the waited-on players.
- **Exactly once.** `processPending` takes the pending round off the session before its first await, so Ready, Start now and a disconnect racing each other cannot process twice.
- **Disconnects.** When a player's last socket in the room closes (release hook `nextRound`) they stop being waited on, which can complete the round. If that empties the set (the only expected player reloading) the round keeps waiting rather than processing. A player who reconnects mid-pending is expected again (not ready) if they are on the map (`join.js`).
- **Processing** (unchanged from unit 9): for each distinct character on a token, in ascending id, where the GM may edit it, `advanceCharacterRound(..., { tickTurnEffects: true })` in its own transaction (turn row first): round effects tick, `round` counters refill, spent actions and follow-ups clear, turn_start / turn_end effects tick by one. Skipped or failed characters are counted. `round:advanced` per character. Every token's movement goes back to full with one `token:move:resetAll`, hidden tokens filtered. The sheet's own Next Round is unchanged.
- **Messages** (never to watchers): `round:pending` (GM: whole state; a player: only their own `{ id, state }`), `round:pending:update` (GM), `round:hold` (GM, with the name), `round:cancelled`, `round:next` (players: the round has started) and `round:done` (GM: `{ advanced, skipped, views }`, whoever completed the round). `state:full` carries a per-role `roundPending`, so a GM or player reload mid-pending restores the state. Players never learn anyone else's readiness.
- **Limits.** If no GM socket is connected when a round completes, the GM's `round:done` goes nowhere and token turn copies stay stale until the next push. Quick rooms process at once because their players are not accounts. Ready and Hold on send the pending round's id; a stale one gets 409 `stale_round`.
